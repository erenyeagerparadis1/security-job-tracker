01 What Kubernetes Actually Is

Kubernetes (K8s) is a container orchestration platform. It takes your containerized workloads and handles scheduling, scaling, networking, and self-healing across a fleet of machines. Think of it as a datacenter operating system: you declare what you want running, and K8s converges reality toward that desired state.

Declarative

You write YAML manifests describing the desired state. K8s controllers continuously reconcile actual → desired.

Self-Healing

Crashed container? K8s restarts it. Node dies? Workloads get rescheduled elsewhere automatically.

Extensible

CRDs, admission webhooks, operators, and CSI/CNI/CRI plugins let you extend every layer.

🔑 Security mental model: K8s is an API-driven system. Every object (pod, secret, role) is a resource in its API. Securing K8s means securing API access, workload isolation, network paths, and the software supply chain.

Component Security Implications

ComponentWhat It DoesIf Compromised…
kube-apiserver Front door for all API calls. AuthN → AuthZ → Admission → etcd. Full cluster takeover. Every object is readable/writable.
etcd Distributed key-value store holding all cluster state, including Secrets. All secrets in plaintext (unless encryption-at-rest). Complete state extraction.
kubelet Runs pods on each node, exposes a local API on port 10250. Exec into any pod on that node, read secrets mounted on that node.

⚠ etcd is the crown jewel. Anyone with direct etcd access bypasses all K8s RBAC entirely. Always encrypt etcd at rest, restrict network access to it, and use TLS client certs.

03 Core Objects

K8s resources are organized in a hierarchy. Understanding this is critical for scoping RBAC and policies.

Object Hierarchy
Cluster-scoped: Node, Namespace, ClusterRole, PV, CRD
↓ contains ↓
Namespace-scoped: Pod, Deployment, Service, Secret, ConfigMap, Role, SA, NetworkPolicy
Pod

Smallest deployable unit. One or more containers sharing network namespace and storage volumes. Every pod gets a unique IP.

Deployment

Manages ReplicaSets for stateless apps. Handles rolling updates and rollbacks. You almost never create bare pods.

Service

Stable network endpoint (ClusterIP, NodePort, LoadBalancer) that load-balances across pod replicas. DNS entry auto-created.

ServiceAccount

Identity for pods. Auto-mounted JWT token used to authenticate to the API server. A key attack vector if over-privileged.

Secret

Base64-encoded (NOT encrypted by default) blobs for credentials, tokens, TLS certs. Mounted as files or env vars.

Namespace

Logical partition for multi-tenancy. RBAC, NetworkPolicy, and ResourceQuotas are scoped to namespaces.

04 Networking Model

K8s networking has three fundamental rules: every pod gets its own IP, every pod can reach every other pod (no NAT), and nodes can reach all pods. This means by default, there is zero network segmentation.

Traffic Paths You Must Secure

Ingress Controller LoadBalancer Svc NodePort
Pod ↔ Pod
East-West (flat by default) DNS-based discovery
Pod → API Server
SA Token auth kubernetes.default.svc
Pod → External
Egress (unrestricted default) DNS exfil
Node → Control Plane
kubelet → api-server etcd client port
⚠ Flat network = lateral movement paradise. A compromised pod can reach every other pod in the cluster by default. NetworkPolicies (§08) are the only in-cluster segmentation mechanism.

06 RBAC (Role-Based Access Control)

RBAC is the authorization layer. It determines who (subject) can do what (verbs) on which resources (objects). There are four RBAC objects:

←binds→

role-least-privilege.yaml
# Good: scoped to specific resources and verbs
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: payments
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
  # ✗ Never use ["*"] for verbs
  # ✗ Never bind cluster-admin to a ServiceAccount

07 Pod Security

The securityContext on a pod/container controls Linux kernel capabilities, user IDs, filesystem access, and privilege escalation. Pod Security Admission (PSA) enforces profiles cluster-wide.

Pod Security Standards (PSA Profiles)
Privileged
No restrictions. System-level workloads only.
Baseline
Prevents known escalations. Sensible default.
Restricted
Hardened. Non-root, drop all caps, read-only root.
hardened-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-app
spec:
  automountServiceAccountToken: false   # don't mount SA token
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    runAsGroup: 10001
    fsGroup: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: registry.example.com/app:v2.1.0@sha256:abc...
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
    resources:
      limits:
        cpu: "500m"
        memory: "256Mi"
✓ Golden rule: Non-root, drop ALL capabilities, read-only root filesystem, RuntimeDefault seccomp, no privilege escalation. Start here and only loosen if the workload genuinely breaks.

08 Network Policies

NetworkPolicies are K8s-native firewalls. They're namespace-scoped and use label selectors to define allowed traffic. Without any NetworkPolicy, all ingress and egress is allowed.

default-deny-all.yaml — APPLY THIS FIRST
# Step 1: Deny everything in the namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: payments
spec:
  podSelector: {}        # matches all pods
  policyTypes:
  - Ingress
  - Egress              # no rules = deny all
allow-specific.yaml — then whitelist
# Step 2: Allow only what's needed
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-api
  namespace: payments
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - port: 8080
      protocol: TCP
🔑 CNI requirement: NetworkPolicies only work if your CNI plugin supports them. Calico, Cilium, and Weave do. The default AWS VPC CNI does not enforce them natively (use Calico addon). Always verify enforcement with a test.

09 Secrets Management

K8s Secrets are base64-encoded, not encrypted by default. Anyone with RBAC access to Secrets in a namespace can read them. They're also visible in etcd unless encryption-at-rest is configured.

Where Secrets Leak
etcd
Stored as plaintext (default)Backup files
API Server
RBAC too broadWatch events
Pod Env Vars
Visible in /procCrash dumpsLogs
tmpfs Mount
On-disk in node memoryContainer escape

Hardening Secrets

Encrypt at Rest

Configure EncryptionConfiguration on the API server with AES-CBC or KMS provider (AWS KMS, GCP KMS, Vault Transit).

External Secrets

Use External Secrets Operator or Secrets Store CSI Driver to sync from Vault, AWS Secrets Manager, etc.

Limit RBAC

Only grant get on specific Secret names, never list or watch on all Secrets in a namespace.

Volume Mounts > Env Vars

Mounted secrets auto-rotate via kubelet. Env vars are baked in at pod start and visible in /proc/1/environ.

12 Service Mesh & mTLS

A service mesh adds a sidecar proxy (Envoy, usually) to every pod, giving you transparent mutual TLS, traffic policies, and observability — without changing application code.

Istio

Most feature-rich. Has AuthorizationPolicy for L7 access control (paths, headers, JWT claims). Heavy operational burden.

Lightweight, Rust-based data plane. Auto-mTLS with zero config. Less L7 policy granularity than Istio.

eBPF-based — no sidecar. Combines CNI + NetworkPolicy + mTLS + observability. Rising standard for security-focused clusters.

14 Hardening Checklist

A senior-level summary of the controls you should implement or verify. Organize your assessment around these layers.

API Server & Control Plane

  • Disable anonymous auth (--anonymous-auth=false)
  • Enable audit logging with a policy that captures mutations to sensitive resources
  • Use OIDC for human auth; short-lived SA tokens for workloads
  • Restrict API server network access (private endpoint or IP allowlist)
  • Encrypt etcd at rest with KMS provider
  • Disable the system:masters group in CI/CD pipelines

Workload & Pods

  • Enforce Pod Security Admission at Restricted level (namespace labels)
  • Run as non-root, drop all capabilities, read-only rootfs
  • Set automountServiceAccountToken: false unless the pod needs API access
  • Set CPU/memory limits to prevent resource abuse (crypto mining)
  • Use RuntimeDefault seccomp profile (or custom)
  • Use AppArmor or SELinux profiles where supported

Network

  • Apply default-deny NetworkPolicy in every namespace, then whitelist
  • Restrict egress — especially block 169.254.169.254 (cloud metadata) from pods
  • Use a CNI that supports NetworkPolicy enforcement (Calico, Cilium)
  • Enable mTLS via service mesh or Cilium for east-west encryption
  • Secure Ingress with WAF, rate limiting, and TLS termination

Supply Chain

  • Pin images by digest, not tags
  • Sign and verify images (cosign + policy engine)
  • Scan images for vulnerabilities in CI and continuously in registry
  • Use distroless / minimal base images
  • Restrict image sources with OPA/Gatekeeper/Kyverno allowlists

Secrets

  • Enable encryption at rest for K8s Secrets (EncryptionConfiguration)
  • Prefer external secrets managers (Vault, cloud KMS) via CSI driver or operator
  • Mount secrets as volumes, not env vars
  • Scope RBAC to specific Secret names, not secrets/*

Runtime & Monitoring

  • Deploy runtime threat detection (Falco, Tetragon, or cloud-native equivalent)
  • Alert on: exec into pods, privileged pod creation, SA token usage anomalies
  • Centralize logs (audit, application, system) in a SIEM
  • Run CIS Kubernetes Benchmark (kube-bench) regularly
  • Periodically threat-model with the MITRE ATT&CK for Containers matrix
✓ Tools to know: kube-bench (CIS benchmark), kubeaudit (manifest auditing), Trivy (image + IaC scanning), Falco (runtime detection), OPA/Gatekeeper or Kyverno (policy engine), kubescape (NSA/CISA hardening), Tetragon (eBPF observability).

15 Hands-On: Deploy a Tomcat App

Theory without practice is incomplete. This section walks through taking a typical Java web application packaged as a .war inside a zip and getting it running on Kubernetes — the "insecure-but-working" way first, so you understand the baseline before hardening it in §16.

📦 Scenario: You receive myapp.zip containing a compiled myapp.war, a server.xml with custom Tomcat configuration, and a setenv.sh for JVM options. Your goal: containerize it and deploy to a K8s cluster.

Step 1 — Extract & Examine the Zip

Start by understanding what's inside. Developers often bundle configs, environment-specific properties, and sometimes credentials in the zip.

terminal
# Unpack and inspect
$ unzip myapp.zip -d myapp/
$ tree myapp/
myapp/
├── myapp.war
├── server.xml
├── setenv.sh
└── db-config.properties    # ← watch out — might contain creds!

# Check for embedded secrets
$ grep -ri "password\|secret\|key" myapp/
db-config.properties:db.password=Pr0d_S3cret!   # ← found one
⚠ Red flag: Credentials in the zip. These must be extracted, stored in a K8s Secret (or external secrets manager), and injected at runtime — never baked into the image. We'll address this in §16.

Step 2 — Write the Dockerfile

Use the official Tomcat base image and copy the WAR into the webapps directory. Tomcat auto-deploys it on startup.

Dockerfile
# Start with the official Tomcat image
FROM tomcat:10.1-jdk17

# Remove default apps (manager, host-manager, ROOT) — attack surface
RUN rm -rf /usr/local/tomcat/webapps/*

# Copy in the WAR file
COPY myapp/myapp.war /usr/local/tomcat/webapps/ROOT.war

# Copy custom server.xml
COPY myapp/server.xml /usr/local/tomcat/conf/server.xml

# Copy JVM settings
COPY myapp/setenv.sh /usr/local/tomcat/bin/setenv.sh

# Expose the default Tomcat port
EXPOSE 8080

CMD ["catalina.sh", "run"]
terminal — build & push
# Build the image
$ docker build -t registry.example.com/myapp:v1.0.0 .

# Push to your container registry
$ docker push registry.example.com/myapp:v1.0.0

Step 3 — Create the Kubernetes Namespace

Always deploy into a dedicated namespace — never into default. This scopes RBAC, NetworkPolicies, and resource quotas.

namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: tomcat-app
  labels:
    team: backend

Step 4 — Write the Deployment

A Deployment manages pod replicas and handles rolling updates. This is the "get it running" version — intentionally not hardened yet.

deployment.yaml — basic (unhardened)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: tomcat-app
  namespace: tomcat-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: tomcat-app
  template:
    metadata:
      labels:
        app: tomcat-app
    spec:
      containers:
      - name: tomcat
        image: registry.example.com/myapp:v1.0.0
        ports:
        - containerPort: 8080
        env:
        - name: DB_PASSWORD           # ← BAD: secret in env var
          value: "Pr0d_S3cret!"
        readinessProbe:
          httpGet:
            path: /
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 5
        livenessProbe:
          httpGet:
            path: /
            port: 8080
          initialDelaySeconds: 30
          periodSeconds: 10

Step 5 — Create the Service

A Service gives your pods a stable network endpoint. Use ClusterIP for internal-only access, or LoadBalancer to expose externally.

service.yaml
apiVersion: v1
kind: Service
metadata:
  name: tomcat-app
  namespace: tomcat-app
spec:
  selector:
    app: tomcat-app
  ports:
  - port: 80
    targetPort: 8080
    protocol: TCP
  type: ClusterIP

Step 6 — Expose via Ingress

An Ingress routes external HTTP(S) traffic to your Service. In production you'd terminate TLS here.

ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: tomcat-app
  namespace: tomcat-app
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - host: myapp.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: tomcat-app
            port:
              number: 80

Fix 1 — Harden the Dockerfile (§07, §10)

The base tomcat:10.1-jdk17 image runs as root and includes default webapps that expose management endpoints. Rebuild with a non-root user and digest-pinned base.

Dockerfile.hardened
# Pin by digest, not tag — prevents supply chain hijack (§10)
FROM tomcat:10.1-jdk17@sha256:a1b2c3d4e5f6...

# Remove ALL default webapps — manager, host-manager, docs, examples
RUN rm -rf /usr/local/tomcat/webapps/* \
         /usr/local/tomcat/webapps.dist/*

# Create a non-root user for Tomcat
RUN groupadd -r tomcat && useradd -r -g tomcat -d /usr/local/tomcat -s /sbin/nologin tomcat

# Create a writable work directory (needed at runtime)
RUN mkdir -p /usr/local/tomcat/work /usr/local/tomcat/temp /usr/local/tomcat/logs \
    && chown -R tomcat:tomcat /usr/local/tomcat

# Copy application
COPY --chown=tomcat:tomcat myapp/myapp.war /usr/local/tomcat/webapps/ROOT.war
COPY --chown=tomcat:tomcat myapp/server.xml /usr/local/tomcat/conf/server.xml
COPY --chown=tomcat:tomcat myapp/setenv.sh  /usr/local/tomcat/bin/setenv.sh

# Do NOT copy db-config.properties — secrets come from K8s

# Switch to non-root (§07)
USER tomcat
EXPOSE 8080
CMD ["catalina.sh", "run"]
terminal — build, scan, sign
# Build
$ docker build -f Dockerfile.hardened -t registry.example.com/myapp:v1.1.0 .

# Scan for vulnerabilities before pushing (§10)
$ trivy image registry.example.com/myapp:v1.1.0
# Fix any CRITICAL/HIGH findings before proceeding

# Push and sign with cosign (§10)
$ docker push registry.example.com/myapp:v1.1.0
$ cosign sign registry.example.com/myapp:v1.1.0

# Grab the digest for pinning in K8s manifests
$ docker inspect --format='{{index .RepoDigests 0}}' registry.example.com/myapp:v1.1.0
registry.example.com/myapp@sha256:7f8e9d...

Fix 2 — Extract Secrets from the Image (§09)

The db-config.properties file containing the password was in the zip. We store it as a K8s Secret and mount it as a volume — never an env var.

terminal — create the secret
# Create the secret imperatively (good for one-off; in prod use sealed-secrets or ESO)
$ kubectl create secret generic tomcat-db-creds \
    --namespace=tomcat-app \
    --from-literal=db.password='Pr0d_S3cret!' \
    --from-literal=db.username='app_user'

# Verify it exists (values are base64, not encrypted by default!)
$ kubectl get secret tomcat-db-creds -n tomcat-app -o yaml

Fix 3 — Create a Dedicated ServiceAccount (§05, §06)

Don't use the default ServiceAccount. Create one with automountServiceAccountToken: false since this app doesn't need to talk to the K8s API.

serviceaccount.yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: tomcat-app-sa
  namespace: tomcat-app
automountServiceAccountToken: false  # no API access needed

Fix 4 — Harden the Deployment Spec (§07)

Apply every pod security best practice: non-root, drop capabilities, read-only rootfs, resource limits, seccomp, and mount secrets as volumes.

deployment-hardened.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: tomcat-app
  namespace: tomcat-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: tomcat-app
  template:
    metadata:
      labels:
        app: tomcat-app
    spec:
      serviceAccountName: tomcat-app-sa      # dedicated SA (§05)
      automountServiceAccountToken: false  # belt + suspenders

      # ── Pod-level security context (§07) ──
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        runAsGroup: 10001
        fsGroup: 10001
        seccompProfile:
          type: RuntimeDefault

      containers:
      - name: tomcat
        # Digest-pinned image (§10)
        image: registry.example.com/myapp@sha256:7f8e9d...
        ports:
        - containerPort: 8080

        # ── Container-level security context ──
        securityContext:
          allowPrivilegeEscalation: false
          readOnlyRootFilesystem: true
          capabilities:
            drop: ["ALL"]

        # ── Resource limits (prevent crypto mining) ──
        resources:
          requests:
            cpu: "250m"
            memory: "512Mi"
          limits:
            cpu: "1"
            memory: "1Gi"

        # ── Mount secrets as files, NOT env vars (§09) ──
        volumeMounts:
        - name: db-creds
          mountPath: /etc/secrets/db
          readOnly: true
        # Tomcat needs writable dirs for work, temp, logs
        - name: tomcat-work
          mountPath: /usr/local/tomcat/work
        - name: tomcat-temp
          mountPath: /usr/local/tomcat/temp
        - name: tomcat-logs
          mountPath: /usr/local/tomcat/logs

        readinessProbe:
          httpGet:
            path: /
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 5
        livenessProbe:
          httpGet:
            path: /
            port: 8080
          initialDelaySeconds: 30
          periodSeconds: 10

      volumes:
      - name: db-creds
        secret:
          secretName: tomcat-db-creds
      - name: tomcat-work
        emptyDir: {}
      - name: tomcat-temp
        emptyDir: {}
      - name: tomcat-logs
        emptyDir: {}               # ephemeral, non-persistent

Fix 5 — Apply Network Policies (§08)

Start with default-deny, then whitelist only the traffic paths the application actually needs.

netpol-default-deny.yaml
# Deny all ingress AND egress in the namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: tomcat-app
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
netpol-allow-ingress.yaml
# Allow traffic from the ingress controller only
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-ingress-to-tomcat
  namespace: tomcat-app
spec:
  podSelector:
    matchLabels:
      app: tomcat-app
  policyTypes: [Ingress]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: ingress-nginx
    ports:
    - port: 8080
      protocol: TCP
netpol-allow-egress.yaml
# Allow egress only to the database and DNS
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-tomcat-egress
  namespace: tomcat-app
spec:
  podSelector:
    matchLabels:
      app: tomcat-app
  policyTypes: [Egress]
  egress:
  # DNS resolution (kube-dns)
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
    ports:
    - port: 53
      protocol: UDP
    - port: 53
      protocol: TCP
  # Database (example: RDS on a specific CIDR)
  - to:
    - ipBlock:
        cidr: 10.0.50.0/24     # DB subnet
    ports:
    - port: 5432
      protocol: TCP          # PostgreSQL

Fix 6 — Enable PSA Enforcement (§07)

Label the namespace so Kubernetes rejects any pod that doesn't meet the restricted security profile.

namespace-hardened.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: tomcat-app
  labels:
    team: backend
    # Pod Security Admission labels
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
    pod-security.kubernetes.io/warn: restricted
    pod-security.kubernetes.io/audit: restricted

Fix 7 — Add TLS to the Ingress (§12)

Terminate TLS at the Ingress layer. Use cert-manager to automate certificate provisioning.

ingress-tls.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: tomcat-app
  namespace: tomcat-app
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/force-ssl-redirect: "true"
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - myapp.example.com
    secretName: myapp-tls-cert
  rules:
  - host: myapp.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: tomcat-app
            port:
              number: 80
