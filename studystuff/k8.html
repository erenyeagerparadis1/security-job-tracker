01 What Kubernetes Actually Is

Kubernetes (K8s) is a container orchestration platform. It takes your containerized workloads and handles scheduling, scaling, networking, and self-healing across a fleet of machines. Think of it as a datacenter operating system: you declare what you want running, and K8s converges reality toward that desired state.

Declarative

You write YAML manifests describing the desired state. K8s controllers continuously reconcile actual → desired.

Self-Healing

Crashed container? K8s restarts it. Node dies? Workloads get rescheduled elsewhere automatically.

Extensible

CRDs, admission webhooks, operators, and CSI/CNI/CRI plugins let you extend every layer.

🔑 Security mental model: K8s is an API-driven system. Every object (pod, secret, role) is a resource in its API. Securing K8s means securing API access, workload isolation, network paths, and the software supply chain.

02 Architecture Deep-Dive

A cluster has two planes: the control plane (the brain) and worker nodes (the muscle). Understanding what each component does is essential for knowing what to protect.

Overlay: click to toggle layers
🔑 Can a node run pods from different apps? Yes — by default the scheduler places any pod on any node that has available CPU and memory, regardless of what else is already running there. A node could simultaneously run a frontend pod, a Prometheus pod, and a CoreDNS pod. You only control co-location when you explicitly configure node affinity (attract pods to specific nodes), taints & tolerations (repel pods unless they opt in), or pod anti-affinity (keep two pod types apart). Without those, it's all capacity-driven.

Full Component Reference

Every component visible in the cluster diagram above, explained — what it is, what layer it lives in, and what an attacker gains by compromising it.

Component Layer What It Is & Does If Compromised…
CONTROL PLANE — dedicated servers, never runs workloads
kube-apiserver Control plane The single front door for everything in the cluster. Every kubectl command, every kubelet heartbeat, every controller action hits this. It enforces AuthN → AuthZ (RBAC) → Admission Controllers before touching etcd. Listens on port 6443 with mutual TLS. Full cluster takeover. Every object (secrets, RBAC, pods) readable and writable. An attacker with API server access owns the cluster.
etcd Control plane A distributed key-value store that holds all cluster state — every pod spec, every secret, every RBAC rule. Only the API server should talk to it. Listens on port 2379. Secrets are stored base64-encoded (not encrypted) unless you configure EncryptionConfiguration. Complete cluster state extraction, bypassing all RBAC. All secrets readable in plaintext. Crown jewel — protect with encryption at rest, TLS client certs, and strict network ACLs.
kube-scheduler Control plane Watches for newly created pods that have no node assigned yet. Picks the best node by scoring against resource requests, affinity rules, taints, topology spread, and priority. Writes the chosen node back to the pod spec in etcd via the API server. It never touches the pod directly. Workload steering. An attacker can force sensitive pods (e.g. secret-reading jobs) onto compromised or attacker-controlled nodes where secrets can be harvested.
controller-manager Control plane A single binary that runs dozens of control loops — Deployment controller, ReplicaSet controller, ServiceAccount controller, Node controller, Job controller, and more. Each loop watches the API server for drift between desired state and actual state, and reconciles the difference. If you delete a pod that belongs to a Deployment, the Deployment controller sees the gap and creates a replacement. Control loop hijack. Can create or modify Deployments, ServiceAccounts, and RBAC objects cluster-wide. An attacker controlling this can establish persistent backdoor workloads.
Ingress controller Control plane* A reverse proxy (nginx, Envoy, Traefik) that watches Ingress objects and programs routing rules: hostname + path → Service → pods. Handles TLS termination — it decrypts incoming HTTPS, inspects the request, and forwards cleartext (or re-encrypts with mTLS) to the backend. *Technically runs as pods, often in kube-system or a dedicated namespace. Traffic interception. All inbound traffic passes through it. Compromise lets an attacker inspect, modify, or drop requests before they reach your apps. Also a foothold into the cluster network.
NODE AGENTS — run on every worker node as OS processes
kubelet Node agent The control plane's agent on each node. Watches the API server for pods assigned to its node, then instructs the container runtime (containerd) to pull images and start containers. Runs liveness/readiness probes. Reports node and pod status back to the API server every ~10s. Exposes a local API on port 10250 — this is what kubectl exec and kubectl logs tunnel through. Exec into any container on that node, read all secrets mounted on that node, and potentially pivot to the node OS itself. Port 10250 exposed to the internet = immediate full-node compromise.
kube-proxy Node agent Programs iptables or IPVS rules on each node to implement Service routing. When a Service gets a ClusterIP, kube-proxy makes sure traffic to that virtual IP gets load-balanced across the healthy pods backing it. It doesn't handle actual packet forwarding — it just programs the kernel networking rules that do. Traffic interception and MITM on the node's network. Can redirect Service traffic to attacker-controlled endpoints, silently stealing credentials or sessions.
CRI runtime
(containerd / CRI-O)		 Node agent CRI stands for Container Runtime Interface — the standard API that kubelet uses to manage containers without caring about the underlying implementation. containerd (most common) and CRI-O are the two main runtimes. They pull images from registries, create containers using Linux namespaces and cgroups, manage their lifecycle, and stream logs. The runtime is what actually calls the kernel to create the isolation boundary around your container. Container escape amplification. A vulnerable runtime (e.g. runc CVE) lets a container break out to the node OS. Attacker then has access to all other containers' filesystems and the kubelet API.
WORKLOAD PODS — your application, running in namespaces
Pod: frontend ns: payments Your user-facing application — a React app, a Tomcat servlet, an nginx serving static assets. It gets its own IP inside the cluster, listens on a port (e.g. 3000), and is exposed to the internet via the Ingress controller. Has no inherent K8s awareness — it's just a process that thinks it's on a normal Linux machine. If compromised, an attacker gets a foothold inside the cluster network. Can attempt lateral movement to other pods, scrape the SA token to hit the API server, or try to reach cloud metadata endpoints (169.254.169.254) to steal IAM credentials.
Pod: api ns: payments Your backend application — a REST or gRPC service that the frontend talks to. Typically holds a ServiceAccount token that grants it permission to read its own ConfigMaps or Secrets. Connects outward to a database or message queue. Often run as multiple replicas spread across nodes for HA. Higher value target than frontend — usually has DB credentials mounted, wider RBAC permissions, and can reach internal services the frontend cannot. A compromised API pod is often the pivot to database exfil.
OBSERVABILITY & RUNTIME SECURITY — ns: monitoring
Prometheus ns: monitoring A time-series metrics database that scrapes /metrics endpoints from every pod, node, and K8s component. Stores CPU, memory, request rates, error rates, and custom app metrics. Often paired with Grafana for dashboards and Alertmanager for alerts. Uses a pull model — Prometheus goes out and fetches metrics rather than waiting to receive them. Metrics exposure. Prometheus can reach /metrics endpoints across namespaces — if its RBAC or NetworkPolicy is too broad, a compromised Prometheus pod can enumerate all services and scrape sensitive telemetry. Also: Prometheus itself often has no auth by default.
Falco ns: monitoring A runtime threat detection engine by Sysdig (CNCF project). Uses eBPF or kernel module to intercept syscalls cluster-wide and match them against a rule engine. Can detect: shell spawned in a container, sensitive file read (e.g. /etc/shadow), outbound connection to unexpected IP, container escape attempts. Sends alerts to Slack, Elasticsearch, or a SIEM. Think of it as an IDS that watches kernel syscalls rather than network packets. Blind spot. If Falco is taken down or its rules are bypassed, the cluster loses its runtime detection layer. Attackers target Falco specifically to operate undetected. Protect with strict RBAC and verify Falco alert pipelines are live.
CLUSTER INTERNALS — ns: kube-system (high-value targets)
CoreDNS ns: kube-system The DNS server for the entire cluster. Every pod resolves Service names (e.g. postgres-svc.payments.svc.cluster.local) by querying CoreDNS at the cluster DNS IP (10.96.0.10 by default). It watches the API server for Service and Endpoint changes and updates its DNS records automatically. Without CoreDNS, pods can't find each other by name — only by raw IP. DNS poisoning and exfiltration. A compromised CoreDNS can redirect traffic — change postgres-svc to point to an attacker's IP. Also: attackers use DNS queries to exfiltrate data from pods even when all TCP egress is blocked (DNS tunneling).
Cilium / Calico
(CNI plugin)		 ns: kube-system The CNI (Container Network Interface) plugin — the component that actually implements the K8s network model. Runs as a DaemonSet (one pod per node). Responsible for: assigning pod IPs, programming routes so pods across nodes can talk, and enforcing NetworkPolicies. Cilium uses eBPF to enforce policies at the kernel level without iptables. Calico uses iptables or its own data plane. Without a CNI plugin, pods have no network connectivity at all. Cilium also adds Hubble for network observability and can enforce mTLS via Wireguard. Total network control. Compromise of the CNI plugin = ability to intercept or drop any traffic in the cluster. Can bypass all NetworkPolicies. Also runs as privileged with host network access — a highly sensitive attack surface.
⚠ etcd is the crown jewel. Anyone with direct etcd access bypasses all K8s RBAC entirely. Always encrypt etcd at rest, restrict network access to it, and use TLS client certs.

03 Core Objects

K8s resources are organized in a hierarchy. Understanding this is critical for scoping RBAC and policies.

Object Hierarchy
Cluster-scoped: Node, Namespace, ClusterRole, PV, CRD
↓ contains ↓
Namespace-scoped: Pod, Deployment, Service, Secret, ConfigMap, Role, SA, NetworkPolicy
Pod

Smallest deployable unit. One or more containers sharing network namespace and storage volumes. Every pod gets a unique IP.

Deployment

Manages ReplicaSets for stateless apps. Handles rolling updates and rollbacks. You almost never create bare pods.

Service

Stable network endpoint (ClusterIP, NodePort, LoadBalancer) that load-balances across pod replicas. DNS entry auto-created.

ServiceAccount

Identity for pods. Auto-mounted JWT token used to authenticate to the API server. A key attack vector if over-privileged.

Secret

Base64-encoded (NOT encrypted by default) blobs for credentials, tokens, TLS certs. Mounted as files or env vars.

Namespace

Logical partition for multi-tenancy. RBAC, NetworkPolicy, and ResourceQuotas are scoped to namespaces.

Core Object Reference

ObjectScopeWhat It Is & DoesSecurity Risk If Misused
WORKLOAD OBJECTS
PodNamespace The atom of K8s. One or more containers sharing the same network namespace (same IP, same localhost), same IPC, and optionally the same volumes. Each pod gets a cluster-unique IP. The scheduler places pods on nodes — once placed, a pod doesn't move. If the node dies, the pod dies and is recreated elsewhere by its controller. A privileged pod (privileged: true) or one with hostPID/hostNetwork can escape to the node OS. Any pod with a mounted SA token is one API call away from privilege escalation if RBAC is too broad.
DeploymentNamespace Declares the desired number of pod replicas running a given container image. Owns a ReplicaSet which in turn owns pods. Handles rolling updates (gradually replaces old pods with new ones) and rollback (revert to prior ReplicaSet). You never create pods directly in production — you create a Deployment and it manages them. A Deployment with no resource limits is an open door to crypto-mining or DoS via resource exhaustion. Image tags without digest pinning let a supply chain attack silently swap the image on the next restart.
DaemonSetNamespace Ensures exactly one pod runs on every node (or a subset). Used for node-level agents: log shippers, Falco, Cilium, node exporters. When a new node joins the cluster, the DaemonSet automatically schedules a pod on it. DaemonSets often need privileged access to the host (Falco needs kernel access, Cilium needs host networking). A compromised DaemonSet pod runs on every node — instant cluster-wide lateral movement.
StatefulSetNamespace Like a Deployment but for stateful workloads (databases, message queues). Provides stable network identities (pod-0, pod-1…) and ordered, sequential pod creation/deletion. Each pod gets its own PersistentVolumeClaim that is not deleted when the pod is. StatefulSet PVCs persist even after pod deletion — sensitive data can linger on volumes long after a workload is removed. Ensure PVCs are encrypted and cleaned up as part of decommissioning.
Job / CronJobNamespace Job runs a pod to completion (batch tasks, DB migrations). CronJob creates Jobs on a schedule (think cron syntax). Completed pods are retained for log inspection but don't consume resources. Attackers use CronJobs for persistence — a malicious CronJob runs periodically and is easy to miss in a busy cluster. Audit all CronJobs, especially ones in kube-system or with broad SA permissions.
NETWORKING OBJECTS
ServiceNamespace A stable virtual IP (ClusterIP) that load-balances traffic across all pods matching a label selector. Has three main types: ClusterIP (internal only), NodePort (exposes on every node's IP at a static port), LoadBalancer (provisions a cloud LB). CoreDNS creates a DNS entry: svc-name.namespace.svc.cluster.local. NodePort services expose ports on every node's public IP — easy to accidentally expose internal services to the internet. LoadBalancer services create real cloud resources that incur cost and exposure. Audit all Services of type NodePort/LoadBalancer regularly.
IngressNamespace An L7 routing rule object: hostname + path → Service. Requires an Ingress Controller (nginx, Envoy, Traefik) to actually implement the rules. Handles TLS termination via a Secret reference for the TLS cert. Think of it as the config file for your reverse proxy, managed declaratively. Misconfigured Ingress rules can expose internal services. Wildcard hostnames (*.company.com) can be exploited via subdomain takeover. Always enforce TLS; never serve plaintext in production.
NetworkPolicyNamespace A pod-level firewall rule. Selects pods by label and defines which ingress (inbound) and egress (outbound) traffic is allowed. Has no effect unless the CNI plugin enforces it. Without any NetworkPolicy, all traffic is allowed. NetworkPolicy gaps = lateral movement. A single missing egress rule lets a compromised pod reach the cloud metadata endpoint (169.254.169.254) and steal IAM credentials.
CONFIGURATION & IDENTITY OBJECTS
ConfigMapNamespace Stores non-sensitive configuration as key-value pairs. Mounted into pods as files or injected as environment variables. Changes to a mounted ConfigMap are reflected in pods without a restart (within ~1 minute). Not suitable for secrets — no access control beyond RBAC. ConfigMaps are often read by many pods. If someone accidentally stores a password in a ConfigMap, it's readable by anyone with get configmaps permission in that namespace — a surprisingly common mistake.
SecretNamespace Stores sensitive data (passwords, tokens, TLS certs) as base64-encoded values — not encrypted unless you configure EncryptionConfiguration on the API server. Mounted into pods as tmpfs volumes or env vars. Three types: Opaque (generic), kubernetes.io/tls (certs), kubernetes.io/dockerconfigjson (registry auth). Base64 is encoding, not encryption. Anyone with get secrets RBAC permission reads them as plaintext. They're also in etcd unencrypted by default. Prefer external secret managers (Vault, AWS Secrets Manager) synced via CSI driver.
ServiceAccountNamespace The identity assigned to a pod. The API server issues a short-lived JWT token to the pod (mounted at /var/run/secrets/kubernetes.io/serviceaccount/token). This token is what the pod uses to authenticate API calls back to the cluster. Every namespace gets a default ServiceAccount automatically. The single most abused object in K8s attacks. Default SA tokens are auto-mounted in every pod even if not needed. A compromised pod with a broad SA can escalate to cluster-admin in one API call. Always set automountServiceAccountToken: false and create purpose-specific SAs with minimal RBAC.
NamespaceCluster A logical partition inside the cluster. RBAC roles, NetworkPolicies, and ResourceQuotas are all scoped to namespaces. Names must be unique within a namespace but can repeat across namespaces. Think of it as a security domain boundary — not a hard wall, but the primary isolation primitive K8s offers for multi-tenancy. Namespaces are soft boundaries. A ClusterRoleBinding punches through them. kube-system namespace is especially sensitive — any pod running there with broad permissions can affect the whole cluster.
PersistentVolume / PVCCluster / NS PersistentVolume (PV) is a piece of actual storage (EBS, NFS, local disk) provisioned by an admin or dynamically by a StorageClass. PersistentVolumeClaim (PVC) is a pod's request for storage — K8s binds a PVC to a matching PV. StatefulSets use PVCs to retain data across pod restarts. PVs can be shared across pods if accessMode is ReadWriteMany — a misconfigured shared volume can expose one tenant's data to another. PVs also survive pod deletion by default; sensitive data persists until explicitly deleted and overwritten.

04 Networking Model

K8s networking has three fundamental rules: every pod gets its own IP, every pod can reach every other pod (no NAT), and nodes can reach all pods. This means by default, there is zero network segmentation.

Traffic Path Reference

Traffic PathHow It WorksProtocol / PortSecurity Control Needed
External → Ingress User traffic from the internet hits the Ingress controller (nginx/Envoy). TLS terminates here. The controller routes based on hostname and path to the correct ClusterIP Service. TCP :443 / :80 TLS certificate, WAF rules, rate limiting, DDoS protection. Never expose plain HTTP in production.
Service → Pod (ClusterIP) kube-proxy programs iptables/IPVS rules that rewrite the virtual ClusterIP to one of the backing pod IPs. Load balancing is random by default. The pod never sees the Service IP — it sees its own IP as the destination. Any TCP/UDP NetworkPolicy on the receiving pod to restrict which pods can send to it. mTLS to authenticate the caller's identity, not just their IP.
Pod → Pod (east-west) Direct IP routing via the CNI plugin. No NAT. Pod A at 10.0.1.4 sends packets directly to Pod B at 10.0.2.5 even across nodes. The CNI (Cilium/Calico) programs routes on each node's kernel. Any TCP/UDP Default-deny NetworkPolicy. Without it, any compromised pod can reach every other pod on any port — the classic lateral movement scenario.
Pod → API server Pods that need cluster API access call kubernetes.default.svc (resolves to the API server's ClusterIP). They authenticate with the SA token mounted at /var/run/secrets/…. RBAC then determines what they can do. TCP :443 (HTTPS) Disable SA token automounting on pods that don't need it. Scope SA RBAC to the minimum needed. Audit SA token usage in audit logs.
Pod → External internet Pods can make outbound connections to any external IP by default. Traffic NATs through the node's IP. DNS resolves via CoreDNS which forwards external queries upstream. Any Egress NetworkPolicy to restrict outbound destinations. Block 169.254.169.254 (cloud metadata). Monitor for DNS tunneling (unusually large TXT/AAAA queries).
kubelet → API server The kubelet on each node maintains a persistent HTTPS connection to the API server, sending node/pod status every ~10 seconds and watching for pod spec changes assigned to its node. TCP :6443 mTLS Mutual TLS with node client certs. Node authorization mode restricts each kubelet to only read pods assigned to its own node (prevents node-to-node data access).
API server → kubelet The API server calls the kubelet to execute kubectl exec, kubectl logs, port-forward, and liveness probe checks. This is an inbound connection to the node from the control plane. TCP :10250 HTTPS Restrict port 10250 to control plane IP only at the firewall/security-group level. Never expose to the internet. This port = full exec capability on all pods on that node.
etcd → etcd (peer) etcd cluster members replicate data between each other using the Raft consensus protocol. In HA setups (3 or 5 members), peers must reach each other for leader election and log replication. TCP :2380 mTLS Mutual TLS between etcd peers. Isolate etcd network from all other cluster traffic. Only the API server should be able to reach :2379 (client port). Firewall all other access.

Authentication Method Reference

MethodUsed ByHow It WorksRevocationRisk & Recommendation
X.509 Client CertsAdmins, nodes, internal components Client presents a certificate signed by the cluster CA. The API server extracts CN as username and O as group. Used by kubelet (system:node:nodename), controller-manager, and scheduler. No password or token — just cert + private key in a kubeconfig file. No revocation. To invalidate a cert you must rotate the entire cluster CA, which breaks all existing certs simultaneously. Never give humans long-lived client certs. Use OIDC instead. Short-cert tools (cert-manager, Teleport) mitigate the revocation problem by issuing 1-hour certs.
ServiceAccount JWTPods / workloads The API server (or the TokenRequest API) issues a signed JWT. Pods receive it mounted at /var/run/secrets/kubernetes.io/serviceaccount/token. Since K8s 1.24, tokens are audience-bound (only valid for the K8s API), expiry-bound (1 hour default), and not stored in etcd as Secrets — they're generated on demand by the kubelet via TokenRequest. Short-lived; expires automatically. Revocable by deleting the ServiceAccount. Disable automount (automountServiceAccountToken: false) for any pod that doesn't call the K8s API. Create a dedicated SA per workload — never share the default SA.
OIDCHuman users, CI/CD The API server is configured with an OIDC provider (Okta, Azure AD, Dex). Users authenticate to the IdP and receive an ID token (JWT). They pass this token to kubectl via --token or a credential plugin. The API server validates the token signature against the IdP's JWKS endpoint, extracts username/groups from claims. Tokens expire per IdP settings (typically 1 hour). Revoke at the IdP level. Supports MFA at the IdP. Preferred for all human access. Groups from OIDC claims map directly to K8s RBAC groups — centralize access control in your IdP. Use kubelogin or kubeconfig credential plugins to automate token refresh.
Static Token FileLegacy / testing only A CSV file of token,user,uid,groups loaded into the API server at startup. Any request with a matching Authorization: Bearer header is authenticated. Tokens never expire — they're valid until the file changes and the API server restarts. No expiry. No revocation without API server restart. Plain-text tokens at rest. Never use in production. File requires API server restart to revoke. No audit trail beyond bearer token appearance in logs.
Bootstrap TokensNode join process Time-limited tokens (format abcdef.0123456789abcdef) used only during the node bootstrap process (kubeadm join). Once the node is joined and has its own client cert, the bootstrap token is no longer used. Stored as Secrets in kube-system. Short-lived by design. Auto-deleted after expiry. Delete used bootstrap tokens immediately. Leaked bootstrap tokens let an attacker register a rogue node into the cluster, which then receives pod specs and secrets.
Webhook Token AuthCustom integrations The API server calls an external HTTP endpoint with the bearer token. The webhook responds with a TokenReview object indicating success/failure and the authenticated user identity. Used to integrate with custom auth systems or legacy token stores. Depends on the external system. Adds latency on every API request. The external webhook becomes a critical availability dependency. Ensure it's HA and has circuit-breaking on the API server side.
AnonymousUnauthenticated requests Requests with no credentials are assigned username system:anonymous and group system:unauthenticated. Enabled by default but has no RBAC rights unless explicitly granted. Some health-check endpoints (/healthz, /readyz) are exempt from auth. N/A Disable with --anonymous-auth=false. Alert on any audit log entries from system:anonymous — they should not exist in a hardened cluster.

RBAC Object & Verb Reference

Object / ConceptScopeWhat It DoesSecurity Notes
RBAC OBJECTS
RoleNamespace Defines a set of permissions (apiGroups + resources + verbs) within a single namespace. Has no effect outside that namespace. This is almost always what you want — prefer Role over ClusterRole for application workloads. Scope creep: a Role that grows to include secrets/* or * verbs over time. Review Roles on every release. Prefer small, named roles per workload over a shared "app-role".
ClusterRoleCluster-wide Same as Role but applies across all namespaces. Also the only way to grant access to cluster-scoped resources (Nodes, PersistentVolumes, Namespaces). Used by built-in roles like cluster-admin, view, edit. Binding a ClusterRole to a subject grants permissions in every namespace, including kube-system. Only create ClusterRoles for platform-level actors (cluster operators, monitoring agents) — never for application SAs.
RoleBindingNamespace Attaches a Role (or a ClusterRole) to a subject (User, Group, ServiceAccount) within a namespace. If it references a ClusterRole, the ClusterRole's permissions are scoped down to that namespace only — a useful pattern for reusable role definitions. Verify the subject is exactly right — a typo in a ServiceAccount name silently grants to the wrong identity. Audit with kubectl get rolebindings -A -o wide regularly.
ClusterRoleBindingCluster-wide Attaches a ClusterRole to a subject cluster-wide. Every namespace, every resource. Needed for cluster-admin users and cluster-level controllers. Very rarely needed for application workloads. High blast radius. Audit all ClusterRoleBindings — there should be very few, and none should reference application SAs or the default SA. Alert on new ClusterRoleBinding creation in production.
VERBS — what operations are allowed
get, list, watchRead get = fetch one resource by name. list = fetch all resources of a type. watch = open a streaming connection to receive change events. Read-only but not harmless — list secrets returns all secret values in a namespace. Never grant list or watch on Secrets to workloads — they only need get on specific named Secrets. watch on pods leaks information about workload churn and scheduling patterns.
create, update, patch, deleteWrite Modify resources. patch is a partial update (JSON merge patch or strategic merge). delete removes the resource. These verbs on sensitive resources (Pods, Secrets, RoleBindings) are high-risk. create pods = run arbitrary workloads. patch deployments = swap container images. delete networkpolicies = remove all network segmentation. Audit these verbs carefully.
escalateDangerous Allows creating a RoleBinding that grants permissions the subject doesn't already have — effectively bypassing the "you can only grant what you have" safety rule. Without this verb, creating a RoleBinding is still subject to privilege escalation checks. Never grant. Any subject with escalate can grant themselves cluster-admin in one step. This verb exists only for bootstrapping purposes.
bindDangerous Allows creating RoleBindings or ClusterRoleBindings that reference a specific Role. A subject with bind on a Role can attach that Role to any other subject, including themselves. Privilege escalation path. If you have bind on cluster-admin ClusterRole, you can bind it to yourself. Alert on any use of this verb.
impersonateDangerous Allows sending requests as a different user, group, or ServiceAccount using the Impersonate-User header. Legitimate use: operators acting as another user for debugging. The API server records the impersonated identity in audit logs. A subject with impersonate can act as any user including cluster-admin, bypassing their own RBAC. Restrict to specific trusted operator SAs only. Alert on any impersonation in audit logs.
DANGEROUS ANTI-PATTERNS
Wildcard ["*"] verbs or resources— Granting all verbs on all resources. Often seen in dev clusters "just to get things working." Includes dangerous verbs (escalate, bind, impersonate) even if you didn't intend to. Any pod or user with wildcard perms = effective cluster-admin. Scan for wildcards with kubectl get clusterroles -o yaml | grep '"*"'.
Binding cluster-admin to a ServiceAccount— Giving a pod the cluster-admin ClusterRole. Common in CI/CD pipelines and Helm deployments that ask for broad permissions. One compromised pod = full cluster takeover. The single most dangerous RBAC mistake. Audit all bindings that reference cluster-admin. CI/CD should use scoped, short-lived tokens instead.
ClusterRoleBinding where RoleBinding suffices— Using cluster-scoped binding when the workload only needs access in one namespace. Often done out of convenience ("it works") without realising the blast radius. Violates least-privilege. If the SA or user is compromised, they have access to every namespace including kube-system. Always prefer RoleBinding + Role within the target namespace.

07 Pod Security

The securityContext on a pod/container controls Linux kernel capabilities, user IDs, filesystem access, and privilege escalation. Pod Security Admission (PSA) enforces profiles cluster-wide.

Pod Security Standards (PSA Profiles)
Privileged
No restrictions. System-level workloads only.
Baseline
Prevents known escalations. Sensible default.
Restricted
Hardened. Non-root, drop all caps, read-only root.
hardened-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-app
spec:
  automountServiceAccountToken: false   # don't mount SA token
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    runAsGroup: 10001
    fsGroup: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: registry.example.com/app:v2.1.0@sha256:abc...
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
    resources:
      limits:
        cpu: "500m"
        memory: "256Mi"
✓ Golden rule: Non-root, drop ALL capabilities, read-only root filesystem, RuntimeDefault seccomp, no privilege escalation. Start here and only loosen if the workload genuinely breaks.

securityContext Field Reference

FieldLevelWhat It DoesRisk If Not Set
POD-LEVEL securityContext — applies to all containers in the pod
runAsNonRoot: truePod Prevents any container in the pod from running as UID 0 (root). The container runtime refuses to start if the image's default user is root and no override is set. Forces images to be built with non-root users. A root process inside a container that escapes via a kernel vulnerability has immediate root on the node. Non-root doesn't prevent escape but massively reduces post-escape impact.
runAsUser / runAsGroupPod Sets the specific UID/GID the container process runs as. Overrides whatever the Dockerfile specifies. fsGroup sets the GID that owns mounted volumes — needed so the process can actually read its own secrets. Without explicit UID setting, you rely on the image Dockerfile to have set a non-root user. Many official images still default to root — always set this explicitly.
seccompProfilePod / Container Restricts which Linux syscalls the container can make using a seccomp filter. RuntimeDefault uses the container runtime's built-in allowlist (blocks ~300 dangerous syscalls). A custom profile can be even tighter. Blocks syscalls like ptrace, perf_event_open, and kernel module loading. Without seccomp, a container can call any syscall the kernel supports. Kernel exploits like Dirty COW and related container escape techniques rely on syscalls that seccomp blocks. RuntimeDefault stops the majority of known container escape techniques.
sysctlsPod Allows setting kernel parameters (namespaced sysctls only) per pod. Used for tuning network buffers, TCP settings etc. Unsafe sysctls (non-namespaced ones) require explicit allowlisting on the node and affect the whole host. Unsafe sysctls can destabilize the host kernel or weaken security parameters cluster-wide. Block with OPA/Kyverno policy — only allow safe namespaced sysctls in the approved list.
CONTAINER-LEVEL securityContext — applies to one container
allowPrivilegeEscalation: falseContainer Sets the no_new_privs flag on the container process. Prevents the process from gaining more privileges than it started with — even via setuid binaries or sudo. This is one of the most important flags to set. Without this, a process running as UID 1000 can execute a setuid binary (like su or sudo) and escalate to root inside the container. Baseline PSS profile requires this.
readOnlyRootFilesystem: trueContainer Mounts the container's root filesystem as read-only. The process cannot write to /, /tmp, /var, etc. Writable directories must be explicitly declared as emptyDir volume mounts. Without this, a compromised container can write malware, modify binaries, or create cron jobs at the filesystem level. Read-only root forces attackers to work entirely in memory — much harder and leaves no persistence.
capabilities.drop: ["ALL"]Container Drops all Linux capabilities. By default containers retain a subset of capabilities including NET_RAW (raw sockets), SYS_CHROOT, AUDIT_WRITE etc. Dropping all removes every privilege the kernel would otherwise grant. NET_RAW alone enables ARP spoofing and ICMP-based attacks. SYS_ADMIN (in privileged containers) enables kernel module loading = game over. Drop all, then add back only what's genuinely needed (e.g. NET_BIND_SERVICE to bind port <1024).
privileged: trueContainer Gives the container essentially all capabilities and disables most security boundaries — equivalent to running as root on the host. The container can see and modify host devices, mount filesystems, and load kernel modules. Only legitimate use: very low-level system daemons (the CNI plugin itself, for example). Container escape is trivial. privileged: true = immediate full node compromise. Block with PSA Restricted profile and OPA policy. Alert on any privileged pod creation in audit logs.
hostPID / hostIPC / hostNetworkPod hostPID: pod sees all processes on the node. hostIPC: can access shared memory of node processes. hostNetwork: pod uses the node's network stack directly (can reach kubelet API at localhost:10250, bypass NetworkPolicy). All three are serious escape vectors. hostNetwork bypasses all NetworkPolicies and can reach the kubelet API. hostPID lets the container inspect and signal host processes. Block all three in PSA Baseline and above.
POD SECURITY ADMISSION (PSA) PROFILES
PrivilegedProfile No restrictions at all. Allows all securityContext settings including privileged: true, host namespaces, and any capabilities. Used only for system-level DaemonSets that genuinely need host access (Cilium, Falco node agents). Only apply to kube-system or dedicated system namespaces. Label: pod-security.kubernetes.io/enforce: privileged.
BaselineProfile Prevents the most obvious container escape techniques. Blocks privileged mode, host namespaces, dangerous capabilities (SYS_ADMIN, NET_ADMIN etc.), and HostPath volumes. Does not require non-root or read-only filesystem. Good minimum for any workload. Assign to application namespaces as a floor. Label: pod-security.kubernetes.io/enforce: baseline.
RestrictedProfile Full hardening. Requires non-root, drops all capabilities, requires read-only root filesystem or explicit volume mounts, requires seccomp RuntimeDefault or stricter, blocks all host namespaces. The most secure workload posture K8s natively supports. Target profile for all new workloads. Some legacy apps break (Tomcat writing to /work, JVM temp files) — solve with emptyDir volume mounts rather than relaxing the profile. Label: pod-security.kubernetes.io/enforce: restricted.

08 Network Policies

NetworkPolicies are K8s-native firewalls. They're namespace-scoped and use label selectors to define allowed traffic. Without any NetworkPolicy, all ingress and egress is allowed.

default-deny-all.yaml — APPLY THIS FIRST
# Step 1: Deny everything in the namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: payments
spec:
  podSelector: {}        # matches all pods
  policyTypes:
  - Ingress
  - Egress              # no rules = deny all
allow-specific.yaml — then whitelist
# Step 2: Allow only what's needed
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-api
  namespace: payments
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - port: 8080
      protocol: TCP
🔑 CNI requirement: NetworkPolicies only work if your CNI plugin supports them. Calico, Cilium, and Weave do. The default AWS VPC CNI does not enforce them natively (use Calico addon). Always verify enforcement with a test.

Hardening Secrets

Encrypt at Rest

Secrets Approach Reference

ApproachWhat It DoesProsCons / Risks
STORAGE APPROACHES
Native K8s Secret (default) Stores base64-encoded values in etcd. Mounted as files in /var/run/secrets/ or injected as env vars. Simple, built-in, no extra tooling. Zero setup. Works everywhere. Rotates automatically when mounted as a volume. Base64 is not encryption. Anyone with etcd access sees plaintext. Anyone with get secrets RBAC sees all values. Values visible in cluster backups.
K8s Secret + EncryptionConfiguration API server encrypts secrets before writing to etcd using AES-CBC (local key) or a KMS provider (AWS KMS, GCP KMS, Azure Key Vault). Key material is outside etcd. Protects against etcd backup exposure. Transparent to applications. Meets many compliance requirements. With local key: key is still on the API server node. KMS provider adds a cloud dependency and latency. Doesn't protect against RBAC abuse — API server still decrypts on read.
External Secrets Operator (ESO) An operator that syncs secrets from external stores (Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager) into K8s Secrets automatically. You define an ExternalSecret CRD that says where to pull from. Single source of truth in external store. Auto-rotation. Works with existing secret management workflows. Secrets never manually handled by developers. Synced secrets still land in etcd as K8s Secrets — combine with EncryptionConfiguration. ESO SA needs cloud IAM permissions — protect carefully.
Secrets Store CSI Driver Mounts secrets directly from an external provider (Vault, AWS SSM, etc.) as ephemeral volumes into the pod at runtime. Secrets never touch etcd. Rotates automatically during the pod's lifetime. Secrets never in etcd. Rotation is live. Works with Vault, AWS SSM, Azure Key Vault, GCP. Supports syncing to K8s Secret for env var use. Adds a node-level DaemonSet. More complex to set up than ESO. Pod startup latency if the external store is slow or unavailable.
HashiCorp Vault + Agent Injector Vault agent runs as a sidecar or init container, authenticates to Vault using the pod's SA token (Vault K8s auth method), fetches secrets, and writes them to a shared in-memory volume. Supports dynamic secrets (Vault generates DB credentials per pod, auto-expires them). Dynamic secrets with TTLs. Vault audit log. Rich policy engine. No secrets in K8s at all. Industry standard for large orgs. Vault is another HA system to operate. The sidecar adds latency and resource overhead. Vault outage = pod startup failure unless secrets are cached.
INJECTION APPROACHES
Volume mount (file) Secret is written as a file in a tmpfs (in-memory) directory. The app reads the file. Kubelet watches for Secret changes and updates the file automatically — rotation without pod restart. Auto-rotation. Not visible in /proc/PID/environ. Can set file permissions. Best injection method. App must support reading secrets from files (most do). Requires code change if app currently reads from env vars.
Environment variable Secret value is injected as an env var at pod start via valueFrom.secretKeyRef. The value is baked in at container startup — no rotation without a pod restart. Easiest for apps — no code change if app already reads env vars. Works with legacy apps. Visible in /proc/1/environ by any process in the container. Captured in crash dumps, debug tools, and some logging frameworks. Does not rotate — stale value until pod restarts.

Supply Chain Tool Reference

Tool / ConceptCategoryWhat It DoesSecurity Value
IMAGE HARDENING
Digest pinningImage ref Reference images by their SHA-256 content digest instead of a mutable tag. image: nginx:1.25 can change — the registry owner can push a new image to that tag. image: nginx@sha256:abc123... is immutable — it will always pull exactly that byte-for-byte image. Eliminates tag hijacking and supply chain substitution attacks. The only way to change what runs is to change the manifest and go through CI.
Distroless imagesBase image Container images that contain only the application and its runtime dependencies — no shell, no package manager, no curl, no busybox. Google's distroless images are the most common. A distroless Java image has the JRE and your JAR — nothing else. Dramatically shrinks attack surface. No shell = attacker cannot run commands after gaining code execution inside the container. No package manager = cannot install tools. Reduces CVE count from hundreds to tens.
Multi-stage buildsDockerfile Build your application in a fat "builder" image (with compilers, build tools, dev dependencies), then copy only the compiled output into a minimal runtime image. The final image never contains build tooling. Keeps build secrets (e.g. private npm tokens) out of the final image. Shrinks image size. Removes compilers that could be used for on-container compilation of exploit tools.
SCANNING & SIGNING
TrivyScanner Open-source vulnerability scanner by Aqua Security. Scans container images, filesystems, Git repos, Kubernetes manifests, Helm charts, and Terraform. Checks against CVE databases (NVD, GitHub Advisories, OS-specific). Also detects misconfigurations in K8s YAML and detects secrets accidentally baked into images. Fast, comprehensive, free. Integrate in CI (trivy image --exit-code 1) to block builds with critical CVEs. Also run against already-deployed images continuously — new CVEs emerge after images are built.
Grype / SyftScanner / SBOM Grype is Anchore's vulnerability scanner. Syft generates SBOMs (Software Bill of Materials) — a machine-readable inventory of every package inside a container image. Syft output feeds into Grype for vulnerability matching, or into a central SBOM store for supply chain auditing. SBOMs let you answer "which of our deployed images contains log4j?" in seconds during an incident. Increasingly mandated by regulations (US EO 14028, EU CRA).
cosign (Sigstore)Image signing Signs container images and stores the signature in the same OCI registry as the image. Uses either keyless signing (Sigstore's transparency log + OIDC identity) or a traditional key pair. Signatures are verifiable by anyone with the public key or via the transparency log. Proves an image came from your CI pipeline and hasn't been tampered with. At admission time, a policy engine (Kyverno, Gatekeeper) verifies the signature — unsigned images are rejected before they ever run.
ADMISSION CONTROL (policy at deploy time)
OPA / GatekeeperPolicy engine Open Policy Agent is a general-purpose policy engine. Gatekeeper is its K8s admission webhook integration. You write policies in Rego (OPA's DSL) that run against every resource create/update request before it reaches etcd. Examples: "reject images not from registry.company.com", "require all pods to have resource limits", "deny privileged containers". Policy-as-code enforced at admission — misconfigured resources never make it into the cluster. Policies live in Git, versioned, reviewed. The gold standard for K8s policy enforcement in large orgs.
KyvernoPolicy engine A K8s-native policy engine (no separate DSL — policies are YAML). Runs as an admission webhook. Can validate (reject bad configs), mutate (auto-add labels, defaults), and generate (auto-create NetworkPolicies for new namespaces). Easier learning curve than OPA/Rego. Lower barrier to adoption than OPA. Good for teams that don't want to learn Rego. Policies are readable by anyone who knows YAML. Actively maintained CNCF project.
Admission webhooksK8s mechanism The API server can call external HTTP services (webhooks) at two points: MutatingAdmissionWebhook (can modify the incoming object before it's persisted) and ValidatingAdmissionWebhook (can allow or deny the request). OPA/Kyverno/image verifiers all implement these webhooks. The enforcement point for all policy-as-code tools. Critical availability dependency — a broken or unavailable webhook can block all deployments. Always run webhooks in HA and set appropriate failurePolicy (Fail vs Ignore).

Service Mesh & mTLS Concept Reference

Concept / ToolWhat It IsSecurity CapabilityRisk If Absent
CORE CONCEPTS
mTLS (mutual TLS)Protocol Both sides of a connection present X.509 certificates and verify each other. Unlike standard TLS (where only the server proves identity), mTLS also proves the client's identity cryptographically. Inside K8s, each workload gets a SPIFFE/SVID identity certificate encoding its ServiceAccount and namespace. Without mTLS, any pod can impersonate any other pod — just send HTTP traffic to its IP. NetworkPolicy restricts which pods can talk, but not whether one pod can impersonate another once they're allowed to talk.
SPIFFE / SVIDIdentity standard SPIFFE (Secure Production Identity Framework for Everyone) is an open standard for workload identity. An SVID (SPIFFE Verifiable Identity Document) is the certificate that proves a workload's identity — encoded as a URI: spiffe://cluster.local/ns/payments/sa/api. Istio, Linkerd, and Cilium all issue SPIFFE-compatible SVIDs. Without workload identity, your only identity primitive is IP address — trivially spoofable in a flat network. SPIFFE binds identity to the cryptographic certificate, not the network location.
Envoy sidecarProxy A high-performance L4/L7 proxy injected as a sidecar container into every pod by the mesh's MutatingAdmissionWebhook. Intercepts all inbound and outbound traffic transparently (via iptables rules in an init container). The app thinks it's talking directly — it doesn't know Envoy exists. Handles mTLS termination, retries, circuit breaking, metrics, tracing. The sidecar adds ~5-10ms latency and 50-100MB memory overhead per pod. A bug in Envoy affects all pods. The init container requires privilege at pod startup — the trade-off for zero-code-change adoption.
AuthorizationPolicy (Istio)L7 policy Istio-specific CRD that lets you write access control rules at L7 — not just "can pod A reach pod B" but "can pod A reach pod B on path /admin/* with method POST and a valid JWT with claim role=admin". Far more granular than K8s NetworkPolicy which operates at L3/L4 only. Without L7 policy, NetworkPolicy only controls which pods talk — not what requests they make. An attacker who can reach the API pod can hit any endpoint including admin ones.
MESH IMPLEMENTATIONS
IstioService mesh The most feature-complete mesh. Control plane components: Istiod (cert management, config distribution, service discovery). Data plane: Envoy sidecars. Features: mTLS, AuthorizationPolicy (L7 RBAC), JWT validation, traffic shaping, retries, circuit breaking, distributed tracing, Kiali dashboard. Heavy — Istiod adds significant control plane resource usage. The learning curve for AuthorizationPolicy is steep. A misconfigured policy can silently allow or deny traffic. Run in permissive mode first, then enforce.
LinkerdService mesh Lightweight, Rust-based data plane (microproxy instead of full Envoy). Zero-config automatic mTLS between all meshed pods. Simpler operational model than Istio. Policy is less granular — L4 (pod-to-pod) rather than L7 (per-path/method). Excellent latency overhead (sub-millisecond). CNCF graduated project. Less L7 policy capability than Istio — if you need per-path or per-header access control, Linkerd may not suffice. Smaller community than Istio. The Rust proxy reduces the CVE surface area but has a different (smaller) ecosystem.
Cilium (eBPF mesh)CNI + mesh Uses eBPF (extended Berkeley Packet Filter) to implement networking and security at the Linux kernel level — no sidecar proxy required. Combines CNI (pod networking), NetworkPolicy (L3/L4), mTLS via WireGuard, and Hubble (real-time flow observability). Growing rapidly as the preferred approach for new clusters. eBPF requires a relatively modern kernel (5.10+). Less mature than Istio for L7 policy. Hubble is powerful but requires setup. The eBPF programs run in the kernel — a Cilium bug can affect the entire node, not just one pod.

INITIAL ACCESS
Exposed Kubernetes DashboardInitial Access The K8s Dashboard (a web UI) was historically deployed with cluster-admin access and no auth by default. Open kubelet API (:10250)Initial Access The kubelet exposes an authenticated API on port 10250. If anonymous auth is enabled (--anonymous-auth=true) or the port is internet-exposed, an attacker can list pods, read logs, and exec commands into any container on that node without credentials. Firewall :10250 to control plane only. Set --anonymous-auth=false on kubelet. Detect with audit logs: kubelet API calls from unexpected source IPs. SSRF → Cloud Metadata APIInitial Access / Credential Access A Server-Side Request Forgery vulnerability in a pod's application lets an attacker make the pod fetch http://169.254.169.254/latest/meta-data/iam/security-credentials/ — the cloud instance metadata endpoint. Committed to Git, leaked in CI logs, or left in a public S3 bucket. Gives the attacker full kubectl access. Scan Git history with truffleHog or gitleaks. Use short-lived OIDC tokens instead of long-lived client certs. Rotate credentials immediately on suspected leak. Enable audit logs to track what the leaked credential accessed.
EXECUTION & PERSISTENCE
kubectl exec shellExecution The attacker (or an over-permissioned operator) uses kubectl exec -it pod -- /bin/bash to get an interactive shell in a running container. From there they can read mounted secrets, make internal API calls, and explore the cluster network. Requires create pods/exec RBAC permission. Restrict pods/exec verb to specific operator SAs. Malicious admission webhookPersistence / Execution An attacker with API access creates a MutatingAdmissionWebhook that intercepts every pod creation and injects a malicious sidecar (reverse shell, cryptominer, credential harvester). Regularly audit kubectl get mutatingwebhookconfigurations. Restrict who can create webhooks. OPA policy: only allow webhooks from approved services.
CronJob persistencePersistence Attacker creates a CronJob that runs every minute, spawning a pod that phones home, mines crypto, or exfiltrates data. The CronJob controller (not the attacker) creates the pods — attribution is harder. Easy to miss in a busy cluster. Alert on CronJob creation by non-CI principals. Audit all CronJobs regularly, especially those with high-privilege SAs. Kyverno policy: CronJobs require a specific label proving they were created by the approved pipeline.
PRIVILEGE ESCALATION
Over-permissive SA tokenPrivilege Escalation A compromised pod reads its auto-mounted SA token at /var/run/secrets/kubernetes.io/serviceaccount/token and uses it to call the K8s API. If the SA has broad RBAC (list secrets, create pods, etc.) the attacker pivots from app-level compromise to cluster-level control. Disable SA token automounting (automountServiceAccountToken: false). Create dedicated per-workload SAs with minimal RBAC. Audit SA permissions with kubectl auth can-i --list --as=system:serviceaccount:ns:sa.
Privileged container escapePrivilege Escalation A container running with privileged: true or hostPID: true can escape to the host node. With privileged: true: mount the host filesystem (nsenter --mount=/proc/1/ns/mnt -- chroot /host), read all node secrets, install a backdoor. This is a complete node takeover in under 60 seconds. Block privileged containers with PSA Restricted profile and OPA policy. Alert on privileged pod creation immediately in audit logs. Falco rule: container running as privileged. Runtime detection: nsenter or chroot syscall from a container process.
LATERAL MOVEMENT & EXFILTRATION
Flat network lateral movementLateral Movement Without NetworkPolicy, a compromised frontend pod can directly connect to the postgres database on port 5432, the Vault agent on port 8200, the Prometheus metrics endpoint, or any other pod in the cluster. The attacker scans the pod CIDR range, discovers services via CoreDNS, and pivots to higher-value targets. Default-deny NetworkPolicy in every namespace. mTLS to prevent impersonation even when network access is allowed. Cilium Hubble or Falco network rules to detect unusual connection patterns (frontend pod → postgres direct connection).
DNS exfiltrationExfiltration Even when all TCP/UDP egress is blocked by NetworkPolicy, DNS (port 53) is almost always allowed (pods need it to resolve service names). An attacker encodes data in DNS queries to an attacker-controlled domain: c2.attacker.com → stolen-data-chunk-1.c2.attacker.com. Data exfiltrates as DNS query names, bypassing egress controls. Restrict DNS egress to internal CoreDNS only. Monitor DNS query volume and unusual TXT/NULL record queries. Cilium DNS-aware NetworkPolicy blocks lookups of non-allowlisted domains. Alert on pods querying domains never seen before in that namespace.

14 Hardening Checklist

A senior-level summary of the controls you should implement or verify. Organize your assessment around these layers.

API Server & Control Plane

  • Disable anonymous auth (--anonymous-auth=false)
  • Enable audit logging with a policy that captures mutations to sensitive resources
  • Use OIDC for human auth; short-lived SA tokens for workloads
  • Restrict API server network access (private endpoint or IP allowlist)
  • Encrypt etcd at rest with KMS provider
  • Disable the system:masters group in CI/CD pipelines

Workload & Pods

  • Enforce Pod Security Admission at Restricted level (namespace labels)
  • Run as non-root, drop all capabilities, read-only rootfs
  • Set automountServiceAccountToken: false unless the pod needs API access
  • Set CPU/memory limits to prevent resource abuse (crypto mining)
  • Use RuntimeDefault seccomp profile (or custom)
  • Use AppArmor or SELinux profiles where supported

Network

  • Apply default-deny NetworkPolicy in every namespace, then whitelist
  • Restrict egress — especially block 169.254.169.254 (cloud metadata) from pods
  • Use a CNI that supports NetworkPolicy enforcement (Calico, Cilium)
  • Enable mTLS via service mesh or Cilium for east-west encryption
  • Secure Ingress with WAF, rate limiting, and TLS termination

Supply Chain

  • Pin images by digest, not tags
  • Sign and verify images (cosign + policy engine)
  • Scan images for vulnerabilities in CI and continuously in registry
  • Use distroless / minimal base images
  • Restrict image sources with OPA/Gatekeeper/Kyverno allowlists

Secrets

  • Enable encryption at rest for K8s Secrets (EncryptionConfiguration)
  • Prefer external secrets managers (Vault, cloud KMS) via CSI driver or operator
  • Mount secrets as volumes, not env vars
  • Scope RBAC to specific Secret names, not secrets/*

Runtime & Monitoring

  • Deploy runtime threat detection (Falco, Tetragon, or cloud-native equivalent)
  • Alert on: exec into pods, privileged pod creation, SA token usage anomalies
  • Centralize logs (audit, application, system) in a SIEM
  • Run CIS Kubernetes Benchmark (kube-bench) regularly
  • Periodically threat-model with the MITRE ATT&CK for Containers matrix
✓ Tools to know: kube-bench (CIS benchmark), kubeaudit (manifest auditing), Trivy (image + IaC scanning), Falco (runtime detection), OPA/Gatekeeper or Kyverno (policy engine), kubescape (NSA/CISA hardening), Tetragon (eBPF observability).

CLUSTER ASSESSMENT

Can run in CI against manifests before they're deployed, or live against a running cluster. Use in CI to catch misconfigurations before deployment. Use against existing clusters for a full posture baseline. Good complement to kube-bench (kubescape focuses on workload configuration, kube-bench on node/API server config).
kubeauditManifest auditor Audits K8s manifests for security issues: missing securityContext, automounted SA tokens, missing NetworkPolicies, containers running as root, missing resource limits. Runs against YAML files or live cluster. Output is human-readable with remediation suggestions. Shift-left tool — run in CI pipeline on every PR that changes K8s manifests. Catches the most common pod security misconfigurations before they reach the cluster.
RUNTIME DETECTION
FalcoRuntime IDS Uses eBPF or a kernel module to intercept Linux syscalls and match them against a rule engine. Ships with 100+ built-in rules: shell in container, sensitive file read, outbound connection to unexpected IP, container escape attempts, privilege escalation syscalls. Sends alerts to Slack, SIEM, or Falcosidekick aggregator in real time. Always-on in production. The closest thing K8s has to an IDS. Pair with Falcosidekick to route alerts to your SIEM. Tune noisy default rules in the first week — don't turn rules off, tune them to add context (e.g. expected containers that legitimately use /proc).
TetragoneBPF observability Cilium's eBPF-based security observability tool. Provides fine-grained kernel-level visibility: process execution, file access, network connections — all correlated with K8s pod identity. Can enforce policies at the kernel level (kill a process on a policy violation) rather than just alerting. No sidecar required. Use when you need deeper observability than Falco provides, or when you want enforcement (not just detection) at the kernel level. Excellent for incident response — reconstruct exactly what a compromised pod did at the syscall level.
TrivyVulnerability / config scanner Scans container images, filesystems, Git repos, IaC (Terraform, Helm, K8s YAML) for CVEs and misconfigurations. Also detects secrets accidentally embedded in images. Free, fast, comprehensive CVE database coverage. Can run as a K8s operator to continuously scan running images. In CI: block merges/deploys on critical CVEs. In cluster: run Trivy Operator to continuously scan all running pods and report new vulnerabilities as they're discovered in the NVD. Also scan Helm charts for misconfiguration before install.
POLICY ENFORCEMENT
OPA / GatekeeperPolicy engine Open Policy Agent is a general-purpose policy engine. Gatekeeper integrates it into K8s as an admission webhook. Policies are written in Rego — a declarative DSL. ConstraintTemplates define the policy logic; Constraints apply them with parameters. Supports audit mode (report violations without blocking) and enforcement mode. When you need complex, cross-resource policies (e.g. "if a pod has label env=prod, it must also have a resource limit and a non-root securityContext"). Better for orgs with dedicated platform teams who can maintain Rego. Audit mode is invaluable — run in audit first to understand the blast radius before enforcing.
KyvernoPolicy engine A K8s-native policy engine with no separate DSL — policies are YAML. Three modes: validate (reject non-compliant resources), mutate (auto-add missing fields like labels or securityContext defaults), and generate (auto-create companion resources like a NetworkPolicy for every new namespace). Easier to adopt than OPA. When you want policy-as-code without learning Rego. Especially powerful for mutation — automatically add readOnlyRootFilesystem: true as a default, so developers don't have to remember. Generate mode is unique — auto-provisioning NetworkPolicies for every new namespace is a game-changer for multi-tenant clusters.
NETWORK OBSERVABILITY
Hubble (Cilium)Network observability Real-time network flow visibility built into Cilium. Shows every connection between pods with full K8s context (pod name, namespace, label, service). CLI: hubble observe --namespace payments. UI: Hubble UI gives a service dependency graph. Helps write NetworkPolicies by showing you exactly what's talking to what before you enforce deny rules. Use before writing NetworkPolicies — observe actual traffic for a week to understand the real communication patterns, then write policies from the observed flow data. Much safer than guessing and breaking things. Also invaluable during incident response.
NetworkPolicy editorPolicy helper Cilium's open-source NetworkPolicy editor at editor.cilium.io — a visual tool for creating NetworkPolicies. You draw the allowed connections graphically and it generates the YAML. Also validates existing policies and explains what they allow/deny in plain English. Use when authoring complex NetworkPolicies. Much less error-prone than hand-writing selector-based YAML. Share generated policies with developers who aren't familiar with K8s networking — the visual representation makes it instantly clear what's allowed.
